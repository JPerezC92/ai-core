# User story — aicore-adoption-sync

> **Created:** 2026-09-11
> **Title:** AICore adoption synchronization
> **Status:** active
> **Epic:** core-governance
> **Affected areas:** `.aicore/`, `.aicore/adopters.yaml`, `.opencode/agents/`, `.opencode/skills/`, `knowledge/`, `README.md`, `AGENTS.md`, `plans/`

## Persona

- A maintainer of a project that adopted AICore and must receive every applicable upstream core change without losing project-owned behavior, and an AICore maintainer who must confirm that no registered adopter is running stale rules.

## Goal

- **G:** Scaffold the complete applicable AI setup and synchronize it as one accepted upstream revision, with generic upstream-owned Mandatory core sections and destination-owned Project extensions. Only AICore may change mandatory content; synchronization sends those changes while preserving compatible extensions, resolving mandatory conflicts in favor of the core and informing the user. Atomic adoption means complete revision acceptance, not a filesystem-crash transaction guarantee.
  - Done when: every catalog unit is adopted or explicitly `not_applicable` under a machine-checked rule at one lock baseline, `check` exits 0 only when the whole adopter is complete/current/resolved (nonzero otherwise), v1 documents are upgrade-only, and `verify-all` blocks on any registered adopter that is missing, unreachable, stale, or not current.

## Scenario

- Before initial migration or sync, the entire destination must be clean and saved; dirty or uncertain state ABORTS before any destination change. The operation never saves, commits, stashes, cleans or resumes automatically. On a clean run, the model reads complete old/new source, destination and externally prepared result, preserves compatible extensions/identity/records/dependencies, resolves mandatory conflicts with cited notices and applies per-surface versions. All prepared results and approvals are frozen before controls/content writes. Ordinary authorized tools apply and stage reviewed paths, propose a separate complete candidate, check, accept the lock only after success and final-check. Failure stops and reports current state without any backup/checkpoint/rollback or automatic Git restoration. Python verifies mechanical facts/bytes, not prose/version meaning, and never publishes adopter files. `verify-all` checks every registered adopter.
