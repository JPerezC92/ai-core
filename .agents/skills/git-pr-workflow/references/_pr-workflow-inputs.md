# PR workflow inputs

> Input schemas for the pull-request publication workflow: the arguments each command takes, the JSON shapes the supplied files must satisfy, and the exit codes they return. The canonical PR-body presentation format stays in `.agents/skills/git-pr/references/_pr-evidence-format.md`; this file owns only the inputs and outputs of the commands.

Read `scripts/prepare_pr_evidence.ts` and the relevant `scripts/pr_review/` production operations relative to the skill root before use; the two content commands live in `../git-pr/scripts/prepare_pr_review.py`. Inputs are supplied UTF-8 files, not automatically authenticated observations. Missing provenance or inputs block the affected operation; never fabricate them or rebuild local prose from GitHub. Existing owners supply immutable inventory and exact paths using their authorized reads, or the `prepare-local` route derives them through read-only Git reads by that same authorized executor; this offline tool grants no collection or Git authority and makes no GitHub call.

## Workflow command contracts

- `prepare-local`: requires `--pr`, `--base`, `--draft`, `--working-body` and `--output`. `--pr` is a positive integer PR number and `--base` the protected base ref; `--draft` is the creation text and `--working-body` the sole body-only document. The route resolves HEAD and the base ref, computes their merge base, enumerates commit messages, reads changed paths with deletions retained and reads file bodies at the resolved head. It performs no GitHub call and fetches no persisted body.
- `prepare-snapshot`: requires `--draft`, `--working-body`, `--input`, `--paths`, `--output`. It assembles scanner input from the local title and body plus the supplied immutable inventory and exact diff paths. The output is the existing scanner schema with one local title artifact, one local working-body artifact, the supplied commits and files. No remote prose is fetched.
- `snapshot`: lower-level compatibility path with `--input`, `--paths`, `--output`; input is already scanner-shaped. Prefer `prepare-local`, then `prepare-snapshot`, for local authoring; neither path invents collection provenance.
- `verify`: requires `--baseline`, `--current`, `--working-body`; both JSON files require the full capture schema below. Current is the owner's authenticated persisted capture, not a head/body-only object. Every baseline field except body must remain equal, including title and OPEN state, and persisted body must equal the intended working-body bytes. The tool compares supplied data; it does not authenticate, fetch, publish, scan or repair.

## Content command contracts

These two commands stay with the `git-pr` skill; their names and arguments are unchanged.

- `initialize`: `--draft` is the creation text (`Title: …`, blank line, `---`, blank line, body starting `## Summary`); `--working-body` is the sole body-only destination. Creation is exclusive, never overwrite.
- `validate`: requires `--baseline`, `--current`, `--working-body`; optional `--decisions` is required when decision-backed exceptions apply. Both capture files use the capture schema below. Baseline and current must be equal, including the remote body, to detect divergence; they are authenticated by the existing owner, not the tool. They do not replace the locally authored candidate. Summary, breaking changes, test-plan text and finding history are preserved; checked items retain their exact keys. The tool structurally supports completed PASS and accepted ADVISORY, not a successful BLOCK publication.

## Inventory file

The `prepare-snapshot` inventory JSON has exactly `schema` (integer `1`), `pr_number` (positive integer), `head_sha` (7–64 hex characters), `base` (nonblank string), `commit_messages` (nonempty array), and `changed_files` (nonempty array). Each commit entry has `surface: "commit-message"`, nonblank string `source`, and string `content`; each file entry has nonempty root-relative `path` without parent traversal and string `content`. `--paths` is a JSON array of unique exact diff-path strings, equal to the unique file-entry paths. Preserve deleted-file entries and owner-evidenced content; do not omit paths.

## Scanner snapshot file

The `snapshot` input is already scanner-shaped: `schema`, `pr_number`, `head_sha`, `base`, `artifacts`, `changed_files`, with exactly one `pr-title`, one `pr-body` and at least one `commit-message` artifact, each carrying `surface`, `source`, `content`.

## PR capture schema

Both capture files — the `validate` baseline and current, and the `verify` baseline and persisted capture — require the full metadata schema: `number` (positive integer), `headRefOid` (7–64 hex characters), `baseRefName`, `headRefName`, `state`, `title`, `body` (strings; state is `OPEN`, and base/head names and title are nonblank). A head/body-only capture is insufficient. Ownership and enforcement of that seven-field schema belong to the content skill: `.agents/skills/git-pr/scripts/pr_content/domain/records.py` defines it and the content skill's `prepare_pr_review.py validate` command applies it before publication on the candidate and after publication on the persisted capture. The workflow skill's `verify` only compares the persisted capture against the intended capture field for field and byte for byte and never redeclares that schema, so the schema already holds before any publication because `validate` runs on the same capture files first.

## Decisions file

Decisions JSON has exactly `pr_number`, `head_sha` (matching metadata), `not_applicable`, `acceptance`, `debt` (arrays). Every entry has exactly six string fields: `target`, `actor`, `date`, `statement`, `evidence`, `destination`; all except destination are nonblank, date is ISO date, targets are unique within each array. N/A targets are exact unchecked item texts; acceptance targets are exactly the unresolved finding IDs. Debt targets include every DEFERRED finding ID and may additionally name independently authorized follow-ups without artificial findings; each requires nonblank destination. Each accepting actor/date appears in the ADVISORY verdict. Owners establish actual author/user authority from cited evidence; schema acceptance proves none. Each debt record produces exactly one Open debt line, in supplied order: `- target — destination, authorized by actor on date`, substituting supplied literal values. For each DEFERRED finding, Owner / resolution starts with the exact destination followed by ` — ` and its resolution text; the validator compares the prefix before the first ` — ` exactly. Independent follow-ups retain their destination and explicit authority under Open debt in the canonical body format.

## Output creation and exit codes

All output creation is exclusive; occupied paths require explicit lifecycle disposition, never hidden overwrite or competing working-body names. `initialize`, `snapshot`, `prepare-snapshot` and `prepare-local` outputs are exclusive-create; existing files produce IO failure without overwrite. Allocate distinct machine-evidence snapshot paths for actual input revisions through the coordinator; these are not extra Markdown bodies. Keep the single working body, do not silently delete/reuse an occupied output. Other commands do not write files. Exit 0 emits `status: prepared` together with the `command` that produced it; exit 1 reports a business rejection, including a Git-derived one; exit 2 reports a rejected command line (an unknown, missing or malformed argument, including a non-positive `--pr`), an IO/JSON failure, or a Git boundary failure — git absent from `PATH`, a failing `rev-list`/`diff`/`show`/`log` read, a timeout, or non-UTF-8 Git output. None authorizes publication or acceptance.

Validation success is structural only: retain independent evidence review, N/A authority, user acceptance, debt and final combined checks. The exclusive designated writer checks live freshness immediately before its ONE final publication, then verifies saved identity/body, obtains the mandatory fresh attribution scan of the actual persisted body and completes final live reread. The writer owns every row, tick, open-debt entry and the verdict; Herald 📯 (Release Manager) — the sole Git and GitHub executor — performs the single publication against the writer's exact validated body file and returns the persisted capture, and the writer — not Herald 📯 (Release Manager) — verifies it. Stale head/body, failed upload or divergent readback blocks acceptance; no blind overwrite or automatic retry. Later separately authorized factual prose corrections remain serialized after observed release of evidence ownership and preserve all rows/ticks/unrelated prose; every such change still needs its fresh persisted-body scan and readback.
