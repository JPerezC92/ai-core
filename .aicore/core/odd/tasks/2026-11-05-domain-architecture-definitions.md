## Specs

- S1 — Repositories are defined once, normatively, in the shared contract rather than only in a stack guide. Exact requirement: hey seems to be our architecture is not definig about repositories  on  clean architecture can u check it. Acceptance: read `architecture/implementation/architecture.md`; one contract rule states what a repository is, that it is one per aggregate root, that it returns domain objects, that a missing record returns an empty result, that it holds no policy and commits nothing, and that its implementation is an infrastructure adapter.
- S2 — Every kind the domain contains is defined with its identity, invariant and mutability characteristics, plus a test for classifying a given type. Exact requirement: about what domain contains entities value object ... stc. Acceptance: read the domain-classification rule; each kind — entity, value object, aggregate, domain event, domain service, pure rule module, data-only record, port, domain error — carries a definition, and a type that names a domain concept but mutates publicly and defers its rules to callers is classified as a record or a nonconforming model.
- S3 — The entity definition cannot be satisfied by an anemic data bag, and reviewers have an explicit check for it. Exact requirement: and can u check if the documentation ioos being clear what is a entity y told this because it is writing anehmic entioties. Acceptance: read the entity rule and the backend shape; identity, invariant ownership, legal transitions and bypass impossibility are all required, and the reviewer questions name behaviour rather than getters or factories.
- S4 — Aggregates and domain events are defined normatively, with applicability gated so that a project without them is not in violation. Exact requirement: Add aggregates and domain events. Acceptance: read the aggregate and event rules; the root is the only mutation entry point, other aggregates are referenced by identity, an event names a domain fact already produced, a transport or integration message is excluded, and both rules bind only where the kind is used.
- S5 — State change has one sanctioned form and returns a value rather than throwing. Exact requirement: Immutable methods returning Entity | DomainError (Recommended). Acceptance: read the state-change rule; a behaviour method verifies the transition and returns a new valid instance carrying the same identity or a typed domain error value, public setters and writable identity are prohibited, and creation is distinguished from reconstruction from persisted state.
- S6 — The domain folder structure prevents more than one rule-bearing type in a module and gives a growing domain a place to keep each concept together. Exact requirement: and please invertigate how to organize the folder structure on domain i dont want like all entities in 1 file; add arule if it grows with many X files it should have to create its respoctive folder. Acceptance: read the Python guide layout section; one rule-bearing type per module, an aggregate's root, children, owned value objects, events and repository interface share its named folder, a role subfolder appears when a second module of that role exists within the same business-ownership boundary without moving aggregate-owned parts outside that boundary, and no generic multi-concept `entities.py`, `models.py` or `value_objects.py` bucket is permitted.
- S7 — One naming standard applies to every supported language, with language-native filename syntax and one role vocabulary. Exact requirement: i want a standart between languajes on this Use language-native filenames, and something about these thing u know nestjs use the nomenclature like {entityname}.entity.js what do u think about it?? it can be used for python and typescript/jsvascript? Acceptance: read the naming tables; the same role set appears for Python, TypeScript and JavaScript, separators follow each language's convention, class names stay business names, and every implementation guide cites the same table instead of defining its own.
- S8 — Values crossing the boundary are named by the role they play, so a database row and an API payload are never called by the domain entity's name. Exact requirement: what about and order returned raw from database how u will name it, or an order recieved  in a api how u will name it?. Acceptance: read the naming standard; a persisted row and a persistence model have distinct role names located in infrastructure, an inbound payload and an outbound representation have distinct action-and-direction names located at the delivery edge, and each maps to the domain object through one explicit step.
- S9 — The change is limited to architecture definitions and their related documentation, with no implementation change. Exact requirement: for now u will not fix any implementation your task is to upgrade all the architecture definitions; architecture definitions and related thing, not implementations. Acceptance: inspect the feature's commits; no application, skill-script or test source file is modified, and existing naming drift is recorded as debt rather than fixed.
- S10 — The decision is recorded with evidence and propagation, and every applicable guide maps each new rule identifier. Exact requirement: i like your plan create the feature. Acceptance: a research record exists with its sources and limits, an ADR states the decision with alternatives and a propagation map, and each of C8, C9 and C10 appears in the obligation mapping of every applicable implementation guide with a cited identifier.
