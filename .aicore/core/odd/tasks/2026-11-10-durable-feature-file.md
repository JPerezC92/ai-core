## Specs

- S1 — Every non-small feature owns one durable file at `odd/features/<feature>.md`, named for the feature and never dated, created from `odd/features/_template.md`. Exact requirement: "i want to have a durable ligthweigth file for feature stored here G:\projects-personal\ai-core\odd\features, not the feature that is used for the implementation G:\projects-personal\ai-core\odd\tasks tracking". Acceptance: open a new non-small feature and read `odd/features/`; one file exists, named for the feature without a date, and shaped like the template.
- S2 — The file states what the feature is and lists the requirements it must satisfy, one line each. Exact requirement: "a file taht descrive a feature and contain what is should achieve to consider its completed". Acceptance: read the file; one paragraph says what the feature is and every requirement appears as a single `R#` line.
- S3 — The file carries one status, `achieved`, `partial` or `not started`, derived from its ticks. Exact requirement: "i accept achieved / partial / not started". Acceptance: tick some requirements and read the status; it is `partial`, and a validation of the same file reports the same value.
- S4 — A requirement carries a mark only when the feature adopts a standard that already exists, and the mark records where this repository departs from it. Exact requirement: "preserve the marks usage, i told u they are just used when we adopt a feature that already ahve a standart that way we can knw were we change something from the standart". Acceptance: read a feature that adopts a standard; each requirement carries a mark. Read a feature explicit from this repository; no requirement carries one.
- S5 — A tick asserts the requirement holds, and only a change that delivered it may set that tick. Exact requirement: "a ticket point is should be threated as a fidelity source taht tell us taht was completed". Acceptance: read a ticked requirement; the tick was set by the change that delivered it, not by a later change and not without delivery.
- S6 — A change that finds a ticked requirement no longer satisfied flags that requirement and records the failure and its cause in its own record. Exact requirement: "if we in the future for some reason found that a already tick box isnt being acomplishidhed we need to flag it add taht in the requirements too". Acceptance: take a ticked requirement that no longer holds; the change flags it and its record names the failure and the cause.
- S7 — Every change reads the file and records, for each requirement, whether it added one, reworded one, retired one or left it alone; the file lists no change records and holds no work-in-progress state, while a requirement may name the single change that delivered it as its evidence. Exact requirement: "it should be reade if any task collide with the list and change it of introduce new requirements on the list". Acceptance: read a closed record that touched a feature; its Log states what it did to each requirement, the feature file lists no change record beyond a requirement's own delivery pointer, and it holds no in-progress state.
