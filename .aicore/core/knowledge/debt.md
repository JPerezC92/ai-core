# Accepted Debt Register

Records of deferred technical or process debt that are **non-blocking** for release.

## Entry format

Each entry MUST include:

- **ID** — unique identifier (e.g. `DEBT-001`)
- **Date** — when the deferral decision was made
- **Description** — what is deferred
- **Direct evidence** — the evidence that justifies deferral
- **Resolution criteria** — what must be true for the debt to be cleared
- **Explicit deferral decision** — who decided, and when

## Rules

- An accepted debt is nonblocking only when its record here carries direct evidence, resolution criteria, and an explicit deferral decision (see Herald 📯 (Release Manager) spec).
- Disclose the ID and unresolved criteria in any operation report that touches it.
- Clear and retire a resolved debt in the same authorized, committed work unit: delete its entry from this register and preserve complete resolution evidence in the governing feature record and its Log, backed by delivery evidence. Identify the debt, evidence that every resolution criterion is met, validation results, independent review results, and the delivering commit; the commit must carry the resolution evidence or its durable governing-record reference. If a PR exists, its body must also carry that evidence or reference; a PR is not required for retirement. Git history is the permanent record for retired entries; this register holds open debts only. Never open a dedicated PR whose sole purpose is pruning cleared entries — each debt is retired by exactly one authorized, committed resolution work unit.
- **User-directed cancellation.** An explicit user decision may cancel an open debt without satisfying its resolution criteria. Cancellation is not resolution or clearance. Before removing the entry, preserve the user decision, unmet criteria, and supporting evidence in the governing feature record; include the cancellation and its evidence in the authorized delivery. This route does not waive the resolution-evidence requirements for resolved debts.
- **ID allocation.** Each register owns an independent monotonic ID sequence; IDs are never shared across projects or registers. Allocate the next ID as the current high-water plus one, read from this register's own recorded next-ID value — never recomputed from the currently open entries, because retiring an entry erases the maximum and would reuse an issued ID. Gaps are valid history: never refill one, and never reuse a retired ID. If the register has no recorded next-ID, bootstrap it once from the highest identifier ever present in this register's verified history; when that history is unavailable, truncated, or renamed, stop and report the gap instead of guessing a starting value.

## DEBT-048 — ODD lifecycle never orders record closure against PR merge

- **Date:** 2026-11-12
- **Description:** Whether an ODD task record must be `closed` before its pull request merges, or whether closure follows a verified merge, is stated nowhere. Impact: repeated interpretation disputes and inconsistent recommendations, and genuine uncertainty about whether a fully reviewed, user-accepted PR may merge while its record is `active`. Root cause is a sequencing gap, not a contradiction: the rules decouple the events without ordering them, and two rules only imply an order. `.agents/skills/odd-workflow/SKILL.md:148` `### Delivery boundary` says "Closing the feature document is not delivery" and keeps push, PR and merge separately authorized; `:118` `### Close` sets closure's preconditions as every task `done` with a commit reference, `Status: closed`, a `Closed:` date and a `Close:` entry, requiring no merge evidence; `:126` places merge proof in `### Retire a task record`, where the sentence "Closure is not delivery" reads as though closure were tied to delivery; and `.aicore/core/knowledge/release.md:15` forbids bookkeeping commits "solely to record merge or cleanup facts", implying closure belongs before the merge without saying so. Upstream versus AICore: the pinned upstream specification does not define this ordering at all — its step 7 `Close` reports the verified outcome and names a work-unit commit or PR slice as the review candidate, with no delivery-verification stage and no record-retirement policy — so the gap is AICore's own. Desired outcome: one unambiguous lifecycle contract agents follow consistently. Preferred solution: state the existing three stages and their preconditions in the owners that already hold them, adding no new status, validator, agent, service or documentation framework.
- **Direct evidence:** A repository-wide search for record-status and merge co-occurrence returns only the cleanup-proof rule (`AGENTS.md` `### Merged-branch cleanup`), `.aicore/core/knowledge/release.md:15` and `SKILL.md:126` — no rule conditions a merge on record status, and none conditions closure on a merge. `.aicore/core/knowledge/release.md:7` requires only that the release-readiness packet *include* "the open-or-closed status of each task and of the feature", which is a reporting duty rather than a required value. `.aicore/core/odd/features/organic-driven-development.md` R14 restates "closing the record is not delivery; push, PR and merge stay separately authorized". Worked example: `.aicore/core/odd/tasks/2026-11-11-odd-core-simplification.md` is `active` at a user-accepted `[ADVISORY]` PR #176 head, with every task `done` and committed except T7, which carries `commit: pending` because closure itself has no commit yet — and `:118` makes a commit a closure precondition.
- **Resolution criteria:** One authoritative statement, in its existing owner, names closure, delivery and retirement in order and assigns each precondition to its stage: closure requires every task `done` with a commit reference plus the independent acceptance `### Close` already requires, and requires no merge evidence; delivery stays separately authorized with merge user-only; merge proof belongs to retirement. No new status value, validator, agent, service, documentation framework or tracker. Acceptance: applied to one `active` record awaiting merge and to one merged change, it yields the same task statuses, task rows, commit references, PR state, merge evidence and closure decision with no further interpretation, and an independent reviewer confirms it contradicts no other rule.
- **Explicit deferral decision:** Recorded by Cipher 🔓 (Lead Orchestrator) on 2026-11-12 on the user's instruction to verify the existing rules and register the ambiguity as technical debt rather than resolve it in-flight, leaving PR #176 open and its record active meanwhile. Deferred, not waived: the entry records no merge decision, and its existence neither blocks nor unblocks any pull request.
