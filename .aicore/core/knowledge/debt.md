# Accepted Debt Register

Records of deferred technical or process debt that are **non-blocking** for release.

## Entry format

Each entry MUST include:

- **ID** — unique identifier (e.g. `DEBT-001`)
- **Date** — when the deferral decision was made
- **Description** — what is deferred
- **Direct evidence** — the evidence that justifies deferral
- **Resolution criteria** — what must be true for the debt to be cleared
- **Explicit deferral decision** — who decided, and when

## Rules

- An accepted debt is nonblocking only when its record here carries direct evidence, resolution criteria, and an explicit deferral decision (see Herald 📯 (Release Manager) spec).
- Disclose the ID and unresolved criteria in any operation report that touches it.
- Clear and retire a resolved debt in the same authorized, committed work unit: delete its entry from this register and preserve complete resolution evidence in the governing feature record and its Log, backed by delivery evidence. Identify the debt, evidence that every resolution criterion is met, validation results, independent review results, and the delivering commit; the commit must carry the resolution evidence or its durable governing-record reference. If a PR exists, its body must also carry that evidence or reference; a PR is not required for retirement. Git history is the permanent record for retired entries; this register holds open debts only. Never open a dedicated PR whose sole purpose is pruning cleared entries — each debt is retired by exactly one authorized, committed resolution work unit.
- **User-directed cancellation.** An explicit user decision may cancel an open debt without satisfying its resolution criteria. Cancellation is not resolution or clearance. Before removing the entry, preserve the user decision, unmet criteria, and supporting evidence in the governing feature record; include the cancellation and its evidence in the authorized delivery. This route does not waive the resolution-evidence requirements for resolved debts.
- **ID allocation.** Each register owns an independent monotonic ID sequence; IDs are never shared across projects or registers. Allocate the next ID as the current high-water plus one, read from this register's own recorded next-ID value — never recomputed from the currently open entries, because retiring an entry erases the maximum and would reuse an issued ID. Gaps are valid history: never refill one, and never reuse a retired ID. If the register has no recorded next-ID, bootstrap it once from the highest identifier ever present in this register's verified history; when that history is unavailable, truncated, or renamed, stop and report the gap instead of guessing a starting value.
- **Every deferred work item is registered here.** A deferral recorded only in a feature `## Log`, a task record, a review summary, or a final report does not satisfy this register: work that is deferred carries an entry with the fields above, linked to the finding, task or feature that produced it, stating why it was deferred, its impact, and the condition for resolution. Group related items under one entry rather than filing duplicates, and search the register before adding one. Creating or holding an entry is never evidence that the underlying issue is fixed, and it never satisfies an unmet requirement whose criterion the deferred work covers.

## DEBT-062 — PR review responsibilities are encoded as ODD task rows and as a closure prerequisite, coupling record closure to release review

- **Date:** 2026-11-19
- **Description:** An ODD task record can assign an implementation task to the pull-request reviewer at a pull-request-only identity, and the canonical close procedure can require current PR evidence before closure. The result is an artificial dependency in both directions: the record cannot close until release review completes, and a PR review appears to gate implementation acceptance even though it assesses the published delivery. **Impact:** completed ODD implementation work remains `active` waiting on a release event, PR findings are read as implementation defects, and a reviewer's head-bound verdict is mistaken for ODD semantic acceptance. The two lifecycles have different owners, different evidence and different failure modes; conflating them produces a record that cannot state truthfully which requirement is unmet and why.
- **Direct evidence:** `odd/tasks/2026-11-19-agent-execution-readiness.md:192` assigns T8 — "independent whole-feature semantic acceptance of this record at its delivered candidate" — to Inquisitor 🔎 (PR Reviewer), an identity that only exists at a published pull request's immutable head; `:217` lists that same reviewer among the ODD review requirements "at the immutable head under T8"; `:218` declares "T8 covers S1–S12 and is the only acceptance this record needs"; `:180` (S12) requires "publication behavior … evidenced by this record's own pull request's review evidence". The record faithfully encoded the governing instruction rather than inventing it: `.agents/skills/odd-workflow/SKILL.md` `### Completion stages` stage 2 states "Independent semantic review remains a closure prerequisite and, when a PR exists, includes its current evidence as required by `### Close`", and `### Close` states "When a PR exists, verify current PR evidence under its canonical evidence procedure." Both clauses import release review into the closure prerequisite. Observed consequence on 2026-11-19: PR #204 was published and its head-bound review returned `[BLOCK]`, and the record remained `active` with T8 `in progress` for that reason alone.
- **Root cause:** Confirmed. The close procedure treats "when a PR exists" as a reason to require that PR's review evidence, instead of keeping implementation acceptance in the ODD owner and delivery review in the release owner. `.aicore/core/knowledge/release.md` and `.agents/skills/git-pr-workflow/SKILL.md` already place head-bound review inside the release workflow and need no change; the defect is confined to the two `odd-workflow` clauses and to the record that encoded them. The validator is not implicated: `feature_validation/domain/rules.ts` has no PR concept and requires closure evidence only, so no validator change is part of the remedy.
- **Correct boundary:** An ODD task owns its requirements, implementation tasks, required tests and implementation verification, evidence and reporting, and its own closure. PR delivery owns preparation and publication through Herald 📯 (Release Manager), the head-bound review by Inquisitor 🔎 (PR Reviewer), PR findings and follow-up corrections, PR-body evidence publication, and the user's merge decision. Closing an ODD record never approves a PR; an open or blocked PR review never prevents closure of completed ODD implementation work. Independent semantic acceptance remains an ODD closure prerequisite, performed by a reviewer who did not author the delivered content and its evidence, and it is not replaced by, nor a substitute for, the head-bound PR review.
- **Resolution criteria:** in separately authorized work — (a) `### Completion stages` stage 2 and `### Close` state the boundary explicitly: implementation acceptance and closure belong to the ODD workflow, publication and head-bound review belong to release, and neither gates the other; (b) the affected record's task rows contain no PR-review activity, no acceptance task carries a PR-only identity or a head/publication qualifier, and no closure prerequisite depends on a PR event; (c) the resulting lifecycle behavior is demonstrated: a record whose implementation and required verification are complete is closed while a pull request carrying that work is open and unreviewed, with its closure evidence drawn only from ODD-owned sources, and that demonstration is recorded in the delivering commit and the record's Log; (d) the validator's behavior is verified unchanged, so no new gate is introduced. Deleting T8, or closing the record, satisfies no part of these criteria on its own.
