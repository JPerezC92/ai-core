# Pull-request execution procedures

The procedures Herald 📯 (Release Manager) follows for the pre-publication evidence handoff, the pull-request closure precondition, pull-request creation and publication, an authorized pull-request-head update, an authorized factual body correction, the pull-request-head handoff and post-merge branch cleanup. Herald 📯 (Release Manager) is the sole Git and GitHub executor; the authority, scope, gates, dependency ownership and reporting obligations in `.opencode/agents/herald.md` bind this procedure in full and are not restated here. The publication protocol is owned by `.agents/skills/git-pr-workflow/SKILL.md` and is unchanged by this document.

## Applicability

Read this file before supplying the pre-publication evidence handoff, and before any pull-request route: pushing a feature branch for a pull request, creating a pull request, updating a pull-request head, applying an authorized factual body correction, or running the post-merge branch cleanup. The obligation to consult this owner binds the agent; no runtime mechanism enforces the read. A file already read in this session stays applicable — re-read it only when it changed, when the read was incomplete, or when its owner requires a fresh read.

## Pre-publication evidence handoff

Cipher 🔓 (Lead Orchestrator) owns the pull-request content: it authors the publication input through the `git-pr` skill and owns the generated body, the findings records, the test-evidence records, the test-item statuses, the open-debt entries and the readiness statement. That skill never runs a Git or GitHub command, so the evidence it works from is yours to supply. Before the authoring begins, supply Cipher 🔓 (Lead Orchestrator) with:

- **the authenticated merge-base diff** — `git diff "$BASE"...<head-sha>` — the scope evidence for the publication input;
- **the scoped commits** — `git log "$BASE"...<head-sha> --oneline` — the commit set the publication input derives from;
- **the applicable effective-ignore check** — for the exact assigned publication-input path and the assigned generated-body path: confirm the actual path is ignored, including negation rules and whether it is already tracked; merely finding an ignore entry is not proof, and a not-yet-created path is checked prospectively. Not ignored, tracked, denied, failed or inconclusive is reported to Cipher 🔓 (Lead Orchestrator) with the checked path and the observed blocker, for separately authorized remediation by the existing ignore-configuration owner. You never edit `.gitignore` or other ignore configuration; while remediation is blocked, pending or declined, you create neither the publication input, the generated body nor the directory, and never hand off a stale file as ready.

Report the observed output of each command, not a summary of it. The diff content, the commit subjects and the ignore-check result are the evidence Cipher 🔓 (Lead Orchestrator) analyzes; it never runs a Git or GitHub command to obtain it.

## Pull-request closure precondition

Pull-request management may not begin until the governing ODD task record is closed and its closure is committed. This binds only the delivery routes that begin or extend that management — pushing a feature branch for a pull request, creating a pull request, and updating a pull-request head. It never restricts `gh pr view` reads, issue operations, tag inspection, or the post-merge branch cleanup in `## Post-merge branch cleanup`.

Before any of those routes, resolve one of three outcomes and stop on the third:

1. **A governing record applies.** Produce the closure proof from committed state, never from the working tree: `git status --porcelain=v1 -- <record>` empty; `git show HEAD:<record>` carrying `Status: closed`, a real `Closed:` date, and every task row `done` with a 7–64 character hexadecimal reference; `git merge-base --is-ancestor <each referenced commit> HEAD` succeeding for each; and `validate_feature.ts <record>` returning `ok`. A missing element is a refusal — including a closure that exists only as an uncommitted edit, and a record whose closed state does not correspond to the commit being processed.
2. **No governing record applies.** This route exists only through the small-work classification in `.aicore/core/knowledge/agent-workflow.md` `### ODD protocol` step 4 — understood, risk-contained, and resumable from the request plus diff — with the artifact-free constraint step 5 states, namely that small and read-only work create no durable feature artifact. Read the bounded applicable section of that owner — `### ODD protocol`, steps 4 and 5 — before accepting this route; it is the authority for the classification tests and for the artifact-free constraint, and the summary here does not replace it. Require that classification to address all three tests individually and to name its evidence for each, and report the classification and its evidence to Cipher 🔓 (Lead Orchestrator). Refuse a bare "ODD not applicable", a classification leaving any test unaddressed, one contradicted by the changed-path set, and one asserted for a change whose own diff adds or modifies an `odd/tasks/` record. The absence of `odd/tasks/` paths in a diff does not by itself establish that ODD is inapplicable.
3. **Anything else** — refuse.

Report a refusal to Cipher 🔓 (Lead Orchestrator) with the exact failing condition and the commands and observed output that established it. Do not report readiness, generate a body, or push a delivery branch while a refusal stands.

## Pull-request creation and publication

Consume Cipher 🔓 (Lead Orchestrator)'s publication input and the body `git-pr` generated from it; you never invoke the content-authoring skill and never author that content yourself. The generated creation body keeps the canonical format's initial shape — `## Summary`, `## Test plan` with `- [ ]` items, and the literal `## Findings / blockers` / `No review findings yet.` placeholder.

Create the initial pull request using the title recorded in the generated publication receipt and the assigned context's generated body-only artifact (`output/pr-working-body.md` is the single-context default), never hand-authored Markdown. Initial creation is separate from Cipher 🔓 (Lead Orchestrator)'s one completed evidence-body upload; no intermediate evidence-body uploads. Follow the publication procedure in `.agents/skills/git-pr-workflow/SKILL.md` through Cipher 🔓 (Lead Orchestrator)'s currently authorized execution route, not ad-hoc pull-request-specific helpers or new grants. Any skill safety blocker, including a failed or unverified effective-ignore preflight, stops preparation or publication; never substitute an absent or stale publication input or bypass the blocker. The publication input and the body generated from it remain the sole pull-request content source; raw diffs, source bodies and history dumps are not content sources.

## Cipher-authorized update of an open pull-request branch

This is the only additional pull-request-head merge route. Act only on Cipher 🔓 (Lead Orchestrator)'s explicit authorization naming the pull request to update; ordinary user authorization to push or open a pull request is not enough. Authenticate fresh live metadata for that exact pull request and require it to be OPEN. Pin its pull-request number, head repository/branch and `headRefOid`, base branch, and the fetched base commit SHA. Verify the intended base and that the selected push remote owns the authenticated head. Require the working checkout to resolve exactly to the pinned head and be clean. Preserve all pre-existing worktree exclusions and other work: if the branch is dirty or already checked out, leave it untouched and use an isolated clean worktree or temp branch at the pinned head; if isolation or identity cannot be verified, stop.

Fetch the current base, then merge it into the authenticated head with `git merge --no-commit --no-ff "$BASE"`. Resolve only conflicts within the explicitly authorized task scope; an out-of-scope conflict is a hard stop. Inspect the complete merge result and exact diff, preserve exclusions, and stage only explicit conflict paths as required. Finish with a new reviewable merge commit using the existing commit-message and explicit-staging rules; never amend, rebase, force-push, or merge the pull request into its base.

Immediately before pushing, re-read live pull-request metadata and fetch the base again. Require the same OPEN pull request, head repository/branch and pinned head OID, base branch and pinned base SHA; require the local merge commit to descend from the pinned head. If the head or base moved, identity differs, a protection rejects the update, a conflict is out of scope, or the normal push is non-fast-forward/rejected, stop without overwrite. Pin the exact local merge-commit SHA, then push ordinarily to the verified head remote and ref (never `$BASE` or `$BASE_BRANCH`); the push itself must remain fast-forward-only. Re-read live metadata for the pull-request number, state, head repository/branch/OID, and base branch, and fetch the base after the push. Require the same pull-request number and OPEN state, same head repository and branch, same intended base branch and pinned base SHA, and live `headRefOid` equal to the exact merge-commit SHA just pushed. If any value differs or cannot be verified, report the expected and exact observed metadata to Cipher 🔓 (Lead Orchestrator) and stop without another push, overwrite, or acceptance. If the base moved during the push race, report the pushed head and current base and stop further acceptance.

After a successful update, pin the new live immutable head and return it with the exact base, diff command, and changed-file list to Cipher 🔓 (Lead Orchestrator). Every prior head-bound snapshot, scan and evidence record is invalid and must be re-established against the new immutable head before readiness is reported. Retain the head checkout and exclusions until the delivery is reported ready and the user decides; this route grants no cleanup or pull-request-merge authority. Never substitute `gh pr update-branch` as a conflict-resolution route.

## Authorized factual prose correction

For an already-authorized, in-scope, reversible factual wording or count correction to an existing pull-request body:

1. First obtain observed release of Cipher 🔓 (Lead Orchestrator)'s pull-request-body ownership: the join is complete, prior access has ceased and no competing writer is active. Acquire the exclusive prose-writer assignment; a stop request or stale timestamp is not release evidence.
2. Then fetch `gh pr view <number> --json number,headRefOid,body`. Verify the expected pull-request identity, reviewed immutable head and accepted handoff body and freshness; missing expectations or divergence blocks. Retain this fresh live body as the mutation baseline, not the saved publication input or a saved body.
3. Compute only the minimal authorized factual delta supported by the verified publication input for that pull request's assigned context (`output/pr-publication.json` is the single-context default) and its verified publication and diff facts. Apply that delta TO THE FRESH LIVE BODY to prepare the body-file under `output/`, never the repository root. Preserve every evidence record, tick and unrelated prose byte-for-byte. Never replace the live body with the publication input or with a regenerated body, even if that input was once authoritative; evidence and tick corrections belong to Cipher 🔓 (Lead Orchestrator), not this path.
4. Immediately before mutation, re-fetch the same pull request, head and body and require exact equality with the baseline. Abort on any changed head or body, failed read or identity mismatch — never overwrite or silently rebase a stale patch. With existing authority and exclusive ownership still valid, perform ONE `gh pr edit <number> --body-file <file>` write.
5. Live-reread `gh pr view <number> --json number,headRefOid,body`; require the same pull request, head and exact intended corrected body, with preserved evidence, ticks and unrelated prose. Failed or divergent reread blocks acceptance; do not issue a second overwrite. Report what was wrong, the corrected fact and its verified source, plus the reread result and ownership release.
6. Do not ask for permission again when existing authority already covers this in-scope reversible correction. This path confers no new Git, release, merge, title, or configuration authority.

Stop and report instead — do not patch — for: a scope change, unsupported facts, a destructive action, missing authority, or a stale or divergent head or body.

This path is separately authorized from the generated publication content: it keeps its own independently prepared body-file under `output/`, its own ownership and its own write authority, and it never restores a stale publication input or body.

## Pull-request-head handoff and retained checkout

After `gh pr create`:

- Obtain the live immutable head with `gh pr view <number> --json number,url,headRefName,headRefOid,baseRefName,state`; confirm it is open, targets `$BASE_BRANCH` unless Cipher 🔓 (Lead Orchestrator) authorized another base, and that `headRefName` is the pushed branch.
- Confirm the retained worktree is exactly that head SHA and keep the head checkout and its review context intact: if the local checkout cannot resolve to `headRefOid`, stop and report the mismatch to Cipher 🔓 (Lead Orchestrator) and offer no evidence context from a branch name or local `HEAD` alone; do not run `git checkout "$BASE_BRANCH"` or perform other cleanup until the delivery has been reported ready and the user's merge decision is recorded.
- Record `git diff --name-only "$BASE"...<head-sha>` as the exact changed-file list and preserve any pre-existing worktree exclusions discovered before this release operation. Do not stage, delete, overwrite, or otherwise absorb those exclusions.
- Return a handoff packet to Cipher 🔓 (Lead Orchestrator): exact branch, immutable head SHA, pull-request number and URL, base `$BASE`, literal diff command `git diff "$BASE"...<head-sha>`, changed-file list, pre-existing worktree exclusions, and the Git-derived evidence Cipher 🔓 (Lead Orchestrator) may not obtain itself — the patch content of `git diff "$BASE"...<head-sha>`, the commit subjects of `git log "$BASE"...<head-sha> --oneline`, and the live pull-request metadata capture `gh pr view <number> --json number,url,state,baseRefName,headRefName,headRefOid,title,body,files`. Cipher 🔓 (Lead Orchestrator) analyzes that evidence; it never runs a Git or GitHub command to obtain it, and an independently requested reviewer receives it only through Cipher 🔓 (Lead Orchestrator).
- The two metadata captures are separate on purpose. The first asserts the pull request's identity before any local work; the second is the handoff's own live capture, taken after the local diff. The local diff changes no remote state, but that fact does not exclude a concurrent remote change, so the handoff carries a capture taken at its own time.
- Include the publication input identity, the generation receipt identity and the generated-body identity, with the authenticated initial remote title and body baseline, in the handoff. Remote reads authenticate identity and freshness and saved results; they never rebuild local authored content.

## Post-merge branch cleanup

Only on a new Cipher 🔓 (Lead Orchestrator) invocation carrying the confirmation that the delivery is reported ready, return the worktree to `$BASE_BRANCH`. If the user has not yet decided on the merge, preserve the head checkout until they do. If source rework is required and authorized, stage a NEW authorized commit (never amend); the reopened record is re-closed and its closure committed per `.agents/skills/odd-workflow/SKILL.md` `### Completion stages` stage 6 before the pull request may return to ready. Evidence-only corrections stay with Cipher 🔓 (Lead Orchestrator); supported already-authorized factual prose follows `## Authorized factual prose correction`, not a source commit or default re-permission request. On user-confirmed merge, never delete a branch before it passes:

- Require accepted review and explicit or standing user authorization covering this cleanup; do not ask again when that authority already exists. Load the project's exact effective permissions before execution; a command-family allow does not validate a target, and external denies are never bypassed. Unrelated stash state is not a cleanup blocker; stash handling stays in `.aicore/core/knowledge/git-execution.md` → `## Stash lifecycle`.
- **Verified pull-request identity.** Read `gh pr view "$PR_NUMBER" --json number,url,state,mergeCommit,baseRefName,headRefName,headRefOid,headRepository,headRepositoryOwner`. Require `state` = `MERGED`, `baseRefName` = `$BASE_BRANCH`, and the intended repository and owner. Pin the pull request's recorded head SHA as `HEAD_REF_OID` and its recorded merge commit SHA as `MERGE_COMMIT`; a missing, empty or unreadable merge commit blocks cleanup. Pin exactly one verified feature branch as `$BRANCH`, never the base branch.
- **Repository identity.** Read `git remote get-url "$BASE_REMOTE"` and resolve the owner and repository from that URL's path. Require them to equal the pull request's `headRepositoryOwner` and `headRepository`. A configured SSH host alias does not change the path comparison; an ambiguous, unreadable or mismatched remote blocks cleanup. When the head lives in a fork, the feature branch belongs to that fork: never delete a fork's branch through the base repository's remote.
- **Prepare.** `git fetch "$BASE_REMOTE"`, safely switch to `$BASE_BRANCH` without overwriting tracked, untracked or ignored work, then fast-forward local base to `$BASE` with `git merge --ff-only "$BASE"`. Preserve unique commits, uncommitted work, exclusions and all stashes; a collision, divergence or unavailable safe switch blocks preparation, never justifies reset, clean or force. This base fast-forward is housekeeping of an already-merged pull request, not permission to merge a pull request.
- **Merge evidence.** Require `git merge-base --is-ancestor "$MERGE_COMMIT" "$BASE"` to succeed: the recorded merge commit must be reachable from the verified base. A failure, a missing object or an unreadable result blocks cleanup. This reachability is the merge proof and is mandatory; matching file contents, `git cherry` and `git branch --merged` never substitute for it.
- **Branch tips.** Require `git rev-parse "$BRANCH"` to equal `HEAD_REF_OID`; a local branch that moved after the pull request merged blocks cleanup, and an absent local branch is skipped, not recreated. Read the remote tip independently with `git ls-remote --heads "$BASE_REMOTE" "refs/heads/$BRANCH"`: an absent remote ref means the branch is already gone remotely and remote deletion is skipped; a differing remote tip blocks cleanup.
- **Occupancy and protection.** Read `git worktree list --porcelain` and require `$BRANCH` in no worktree. When the remote branch exists, confirm through the GitHub API that it is not protected; a protected branch blocks cleanup and is never forced around, and a protection state that cannot be established blocks cleanup.
- **Choose the deletion method from the merge evidence, before any deletion attempt.** `git rev-parse "$MERGE_COMMIT^2"` resolves a second parent only for a merge commit, which makes the head an ancestor of the base; an unresolvable second parent means a squash or rebase merge. A merge commit needs `git merge-base --is-ancestor "$BRANCH" "$BASE"` to succeed and deletes with `git branch -d -- "$BRANCH"`. A squash or rebase rewrite makes the head a non-ancestor even though the work landed, so it needs the verified pull-request identity, the reachable merge commit and the pinned local and remote branch tips before `git branch -D -- "$BRANCH"`. A failed `git branch -d` is never a reason to retry with `-D`.
- **Revalidate, delete one target, verify.** Immediately before each deletion, re-read the live pull-request identity, the merge commit's reachability, the local branch tip and the remote branch tip and require every value to equal the pinned evidence; a changed or unreadable value blocks, and the target is never widened and never retried with force. Delete one verified feature branch per invocation with the method chosen above; remote deletion uses `git push $BASE_REMOTE --delete refs/heads/$BRANCH` only when the freshly read remote tip equals `HEAD_REF_OID` and the branch belongs to the base repository rather than a fork. After deletion, confirm the intended local and remote refs are absent and that user work remains preserved. These are direct Git commands.
