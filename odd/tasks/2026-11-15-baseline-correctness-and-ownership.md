## Specs

- S1 — A distributed payload never contains dependency installation directories, symbolic links or directory junctions, and is identical whether or not the source checkout has its dependencies installed. Exact requirement: "Exclude `node_modules` and other non-distributable dependency directories." and "Do not follow or distribute symlinks or junctions." and "Ensure distributed payloads do not depend on the maintainer's dependency installation." Acceptance: enroll from a dependency-installed source checkout into a disposable destination and list the delivered paths; no path under a dependency directory appears, no link is delivered, and the delivered set equals the set from a dependency-free checkout.
- S2 — The root instruction file the synchronization writes and hosts the reconciliation blocker in is the file the selected editor actually loads, while an explicit root selection is still honoured. Exact requirement: "Correct the `CLAUDE.md` fallback problem." and "Use `AGENTS.md` for the supported OpenCode/Cursor baseline." and "Preserve explicit root selection where appropriate." Acceptance: enroll into a disposable destination whose only instruction file is `CLAUDE.md`; the run refuses and names the explicit root option, and enrolling with an `AGENTS.md` destination writes and later hosts the blocker there.
- S3 — OpenCode configuration is sourced from `.opencode/opencode.jsonc` in the AICore source and delivered to `.opencode/opencode.jsonc` in an OpenCode destination, and no duplicate configuration file is produced at the destination root. Exact requirement: "AICore source and OpenCode destinations use `.opencode/opencode.jsonc`." Acceptance: enroll an OpenCode destination and read its file listing; `.opencode/opencode.jsonc` exists with the source top-level keys and no root `opencode.jsonc` exists.
- S4 — The Context7 secret reference resolves to the destination project's own `.secrets/` directory, never outside the project, and a missing secret file does not cause a read outside the intended project. Exact requirement: "Context7's `{file:...}` reference resolves to the project-root `.secrets/`." and "Missing secret files do not cause unexpected access outside the intended project." Acceptance: with only a non-credential placeholder file under the destination `.secrets/`, the enrolled destination's effective OpenCode configuration substitutes that placeholder into the server header, and with the file absent the header is empty rather than populated from any parent directory.
- S5 — A destination-owned agent model selection survives repeated synchronization. Exact requirement: "Destination-owned model selections survive repeat synchronization." Acceptance: after enrollment, set a model value in a distributed agent's destination-owned key set, run synchronization again, and read the value back unchanged with an updating run reporting success.
- S15 — A configuration setting the core does not define survives repeated synchronization unmodified, including a provider section, a destination default model and an additional named MCP server, while a destination-authored replacement of the core permission list is restored by the next synchronization. Exact requirement: "Core-owned permission settings must survive synchronization and unauthorized destination modifications must be detected or corrected according to the synchronization contract." Acceptance: after enrollment, add a destination-only top-level setting and an additional named MCP server, replace the core permission list, run synchronization again, and observe the destination-only setting and extra server unchanged, the permission list restored to the core's value, and the run reporting success. This check does not claim a runtime security guarantee.
- S16 — On OpenCode enrollment a missing required secret directory is created, an existing secret file is preserved byte-for-byte, a missing required credential file is created empty, and the destination Git ignore file gains an effective `.secrets/` rule without duplicating one or rewriting unrelated rules; Cursor enrollment creates neither. Exact requirement: "If `.secrets/` exists, preserve it." and "If missing and required by the selected configuration, create it." and "If a required credential file exists, preserve its exact contents." and "If missing, create an empty local placeholder without inventing credential values." and "Ensure the destination's `.secrets/` directory is ignored by Git." Acceptance: enroll OpenCode with and without a pre-existing secret file and ignore file; observe the four creation/preserve/ignore outcomes; enroll Cursor and observe no secret directory created.
- S6 — A destination can disable an optional capability at first enrollment and that capability is neither installed nor bound. Exact requirement: "A destination must be able to opt out of optional capabilities without having them reintroduced during subsequent synchronization." Acceptance: enroll with an exclusion declared for one optional capability and list the destination; the excluded resource is absent and no binding records it.
- S7 — A declared exclusion survives later synchronization, including a re-enrollment that enrolls newly added cleared sources. Exact requirement: "Excluded resources must remain excluded, including during `init --bind-cleared`." Acceptance: enroll with an exclusion, add nothing, run the enrollment command again over the same destination, and read the destination listing; the excluded resource remains absent.
- S8 — Disabling a capability that is already installed is reported as outstanding reconciliation until the destination owner removes the files, and no file is deleted by synchronization. Exact requirement: "If removal requires destination-owner action, expose that requirement explicitly through existing reconciliation mechanisms and report the opt-out as pending until resolved." Acceptance: add an exclusion to an enrolled destination that already holds the resource, run verification, and observe a non-zero result naming the outstanding reconciliation with the file still present on disk.
- S9 — Removing an exclusion restores the capability, and a re-enrollment does not silently restore an exclusion the destination owner removed. Exact requirement: "Removing an exclusion must have well-defined behavior. It should not mysteriously restore an exclusion that the destination owner intentionally removed." Acceptance: remove a declared exclusion, run synchronization, and observe the resource delivered again; then remove the exclusion declaration entirely, re-enroll, and observe the resource still delivered.
- S10 — An exclusion that would disable a mandatory baseline or safety contract is refused. Exact requirement: "Reject exclusions that would disable mandatory baseline or safety contracts." Acceptance: declare an exclusion naming the root runtime file or the harness configuration and run the enrollment command; the request is refused with a message naming the protected resource and nothing is written.
- S11 — Distributed configuration references only integrations usable at the destination; source-maintenance-only tooling is not distributed, and local `.secrets/` contents are never distributed. Exact requirement: "Do not leave newly enrolled projects with configurations that reference missing source-local tools." and "validate that local `.secrets/` contents remain undistributed." Acceptance: enroll an OpenCode destination and read its merged configuration; no server entry references a source-only path or executable, and the destination holds no file copied from `.secrets/`.
- S12 — A freshly enrolled Cursor destination is usable: the root instruction file, the shared skills root and all fourteen agent documents resolve at Cursor's native discovery locations, and a later synchronization updates them. Exact requirement: "The Cursor baseline must be genuinely usable, not merely copied into Cursor directories." Acceptance: enroll a disposable Cursor destination, then run synchronization again; `.cursor/agents/` holds fourteen agent documents, `.agents/skills/` holds the shared skills, the instruction file carries the blocker contract, and the updating run reports the destination current after reconciliation.
- S13 — Repository documentation states the configuration location, source versus destination ownership, supported profiles, exclusion semantics, secret-file requirements, distributed MCP behaviour, Cursor limitations, and bootstrap and synchronization behaviour, with no contradictory active structure map. Exact requirement: "Update the repository documentation to accurately describe: The new OpenCode configuration location." and "Correct the inaccurate repository structure documentation. Avoid leaving contradictory active maps." Acceptance: read the documented owner pages and find each named subject stated consistently, and search the active documentation set for the retired configuration location and find no residual claim.
- S14 — Existing synchronization guarantees are unchanged: pinned revisions, fail-closed clearance, region/raw/merge ownership, destination project regions, write-target refusals, pending reconciliation, drift detection, absence of deletion, and Git/GitHub isolation. Exact requirement: "Preserve the existing synchronization engine wherever possible." and "Do not weaken existing write-target safety checks." Acceptance: run the committed test suites and the parity corpus; every pre-existing case still passes, and the pre-existing write-target refusal cases still refuse.
- S17 — OpenCode destinations receive working `astgrep` and `semgrep` MCP launchers that do not name AICore-only filesystem paths; `system-one` remains undistributed. Exact requirement: "Distribute functional `astgrep` and `semgrep` MCP integrations to downstream OpenCode projects." and "`system-one`: preserved in AICore, not distributed." Acceptance: enroll an OpenCode destination and read its merged configuration; `astgrep` and `semgrep` servers are present with launch commands that contain neither `.opencode/tooling/` nor `mcp-servers/`, and `system-one` is absent.
