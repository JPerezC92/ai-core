## Specs

- S1 — The authoritative language-agnostic contract mandates a class for every application use case. Exact requirement: "All application use cases must be implemented as classes, regardless of programming language." Acceptance: read `architecture/implementation/architecture.md` → `## C3 — Application operation`; the rule states that every use case is a class exposing one `execute()` with constructor-injected collaborators, and no text permits a standalone function to stand in for a use-case class.
- S2 — Language guides carry the class-first convention and the stated exemptions. Exact requirement: "Use classes rather than standalone functions. Preserve the `execute()` execution contract. Use constructor injection for required collaborators where applicable. Avoid unnecessary inheritance, interfaces, and abstraction layers. Do not apply this requirement to React components, hooks, or general-purpose utilities." Acceptance: read `architecture/implementation/stacks/python.md` → `## Application operations` and `architecture/implementation/stacks/typescript/react.md` → `## Application operations`; both require a use-case class with `execute()` and constructor injection, neither permits a function-form operation, and the React guide states that components, hooks and general-purpose utilities are exempt.
- S3 — The per-stack function-form decision is retired through the ADR lifecycle. Exact requirement: "Supersede the previous per-stack freedom to use function-based application operations, including the relevant decision in ADR 0005." Acceptance: read `docs/architecture/decisions/0005-use-case-organization-and-naming.md`; it carries a `Superseded` line citing this decision, its date and the governing owner, and its original decision text is unchanged.
- S4 — All tests live under one root-level `tests/` directory with exactly three level directories. Exact requirement: "All tests must be organized under a root-level `tests/` directory." Acceptance: read `architecture/testing/architecture.md` → `## Test organization`; `T10` requires `tests/unit/`, `tests/integration/` and `tests/e2e/` as the only level directories.
- S5 — Colocated and file-per-file testing are prohibited. Exact requirement: "No colocated tests. No tests inside production directories. No automatically generated test for every production file." Acceptance: read `architecture/testing/architecture.md` `T2` and `T10` and both guides in `architecture/testing/stacks/`; no instruction places a test beside an implementation file, inside a production module, or requires one test per production file.
- S6 — The colocation decision in ADR 0002 is retired through the ADR lifecycle. Exact requirement: "Supersede the relevant colocation requirements in T10 and ADR 0002." Acceptance: read `docs/architecture/decisions/0002-testing-architecture-layering.md`; it carries a `Superseded` line citing this decision, its date and the governing owner, and its original decision text is unchanged.
- S7 — Exactly three testing levels, and no invented nested test directories. Exact requirement: "These are the only three testing levels. ... No additional testing levels. No invented mandatory nested test directories." Acceptance: read `architecture/testing/architecture.md` `T1` and `T10`; the three level directories are the only level directories, and no role-named nested directory such as `parsers/`, `entities/`, `value_objects/`, `hooks/` or `helpers/` is mandated.
- S8 — The approved testing boundaries are preserved in the contract. Exact requirement: "Backend unit tests target application use-case classes, with ports mocked. Frontend unit tests target components together with their real hooks, mocking the service module rather than the hook module. Backend integration tests target repository adapters against real isolated databases. Frontend integration tests target service modules with `fetch` stubbed. Backend E2E tests target the assembled HTTP application. Frontend E2E tests target the assembled browser application, preserving the established Playwright three-phase process. Preserve the observable assertion responsibilities defined by the original test pyramid." Acceptance: read `architecture/testing/architecture.md` `T2`, `T4` and `T5`; each approved target and its observable assertion are stated there, including the component-with-its-real-hook unit and the repository adapter against a real isolated store.
- S9 — The parser unit-test row keeps its original scope. Exact requirement: "The existing parser unit-test row must be reviewed for its original scope. Do not expand it into arbitrary file-level testing, invent a `parsers/` directory, or silently remove an existing requirement." Acceptance: read `architecture/testing/architecture.md` `T2` and both guides; the parser/loader unit target is stated explicitly in the contract and retained in each guide, and no `parsers/` directory is introduced anywhere.
- S10 — Python no longer permits independent unit tests of arbitrary domain entities, value objects and helper functions. Exact requirement: "Remove Python-specific permissions for independent unit tests of arbitrary domain entities, value objects, and helper functions." Acceptance: read `architecture/testing/stacks/python.md`; its unit row names one use-case class or one parser/loader and no domain-object or helper unit-test permission remains in its file-organization, unit-test or parity rows.
- S11 — Infrastructure adapters and mapping have a canonical home. Exact requirement: "Use `infrastructure/adapters/` for infrastructure adapter and mapping responsibilities. Preserve a canonical repository structure consistent across languages. Do not create unnecessary directories or wrappers when their responsibilities do not exist." Acceptance: read `architecture/implementation/shapes/backend.md` `B1`/`B3` and the Python and NestJS implementation guides; each names `infrastructure/adapters/` as the adapter and mapping location and states that a directory is created only when its responsibility exists.
- S12 — Canonical organization is shape-scoped and identical across languages, with no `presentation/` directory. Exact requirement: "Canonical directory organization is application-shape scoped: backend, frontend, and scripts may differ where their responsibilities differ, but equivalent architectural responsibilities must be organized consistently across languages. ... Do not introduce `presentation/` as a mandatory directory." Acceptance: read `architecture/README.md` → `## Content model` and the shapes; the shape-scoped canonical layout rule is stated and no document requires a `presentation/` directory.
- S13 — Domain behaviour and external-representation mapping stay separated. Exact requirement: "Domain entities own applicable business invariants and behavior. Value objects encapsulate their relevant domain semantics. Business transformations belong in the domain. External representation mapping belongs in infrastructure. Infrastructure adapters do not own business rules." Acceptance: read `architecture/implementation/architecture.md` `C4` and `C8`; the rule distinguishes a transformation governed by a business rule from a transformation between an external representation and domain data, and states that adapters own no business rule.
- S14 — Conflicting ADRs are amended or superseded without rewriting their history. Exact requirement: "Use the repository's established ADR lifecycle to supersede or amend decisions that conflict with the newly approved architecture. Do not silently delete or rewrite historical rationale." Acceptance: read `docs/architecture/decisions/0002-testing-architecture-layering.md` and `0005-use-case-organization-and-naming.md`; each conflicting decision carries an added status line and its original decision text is byte-unchanged.
- S15 — The change set is documentation only. Exact requirement: "This task authorizes architecture documentation changes, not production implementation changes. ... Prohibited activities: - Modifying production code. - Refactoring domain entities, use cases, repositories, or adapters. - Moving or renaming implementation files. - Migrating existing tests. - Modifying test discovery configuration. - Changing CI pipelines. - Adding or changing dependencies. - Creating architecture enforcement scripts or validators. - Reorganizing existing application directories. - Fixing existing implementation violations as part of this task." - S16 — Evidenced implementation violations are recorded as technical debt, not fixed. Exact requirement: "If you identify existing implementation violations while reviewing documentation, record them as technical debt under the repository's established ODD debt workflow."
