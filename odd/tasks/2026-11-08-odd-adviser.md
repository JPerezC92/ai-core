## Goals

- **G1 — Automatic and fileless.** A new user message with an inline image is evaluated without the user saving a file.
- **G2 — Contract and provenance.** Validate schema, options and input identity before delivery; validation does not prove the recommendation correct.
- **G3 — Evidence-based confidence.** Evaluate bounded use cases independently; constrained output does not guarantee accuracy or resistance to malicious input.
- **G4 — Observable.** Record operational lifecycle, reported disposition and independent assessment separately; logs alone do not establish improvement.
- **G5 — Execution overlay without new permission.** Qualifying findings are default workflow guidance for System 2. They never grant permissions, waive a gate, or override mandatory constraints.
- **G6 — Portable.** Questions and model access live in a portable MCP; only attachment capture and delivery are OpenCode-specific.

## Trust model

| Level | Meaning | Required evidence |
|---|---|---|
| V0 | Rejected | Schema, enum, or provenance failure — never delivered |
| V1 | Contract-valid | Conforms to the versioned question profile; supplied-context identity and coverage are recorded where available |
| V2 | Independently assessed | An independent reviewer has checked a cited action or artifact and recorded the result; an agent's self-report alone is not independent verification |
| V3 | Authoritative | Not reachable by design — authorization stays with the user and main agent |

Delivered advice is **V1 at most**. Agent-reported reasoning, observed action and independent assessment are distinct evidence. The tested `/v1/systemone` choice response includes the chosen option, probabilities and confidence, not citations; adapter provenance cannot prove which input the model used.

## Specs

- S1 — The integration is a thin OpenCode adapter plus a portable System 1 MCP, not an OpenCode-only model client. Exact requirement: `just a plugin to capture images and pass it to an MCP were the system1 will live` and `Automatic on every message`. Acceptance: run the same question-profile evaluation through the MCP without OpenCode; identical validated output is produced.
- S2 — Inline chat images are evaluated without saving a project file. Exact requirement: `i dont want to create a file on the project everytime i need u to read a image`. Acceptance: submit a message with an inline image and no file; the MCP request contains that image data and no path.
- S3 — Only contract-valid answers are delivered; failures degrade explicitly, and delivery claims nothing beyond what the API returns. Exact requirement: `make something like golas to stop flagging it as untrusted and promote it to something that is secure to follow`. Acceptance: submit malformed, out-of-enum, and provenance-mismatched responses; each is rejected at V0 and the message proceeds with an explicit unavailable status. Acceptance also confirms the delivered text does not claim the model cited evidence.
- S4 — Questions and choices are versioned configuration, never improvised per request. Exact requirement: `where will live the chopices` and `u will fabric them everytime`. Acceptance: change the question profile file and observe that subsequent requests carry the new profile version with no source edit.
- S5 — When enabled, a new user message triggers an evaluation attempt; tool continuations reuse its result within a plugin lifetime. Exact requirement: `Automatic on every message`. Acceptance: exercise one message with several tool continuations in one process; only one inference attempt is observed. Reload/restart exactly-once behavior is not claimed.
- S6 — Evaluation records distinguish execution, request inclusion, reported disposition, observed action and independent assessment, including skipped, failed, interrupted and unknown states. Exact requirement: `something to verify if it is working and if is being improved the workflow like something if the main agent followed the instruction of the system1`. Acceptance: inspect a simulated successful and failed evaluation and observe distinct truthful lifecycle states without treating missing evidence as success.
- S9 — Operational records omit raw prompts, screenshots, credentials and file contents by default, while reporting input coverage and omitted/truncated context. Exact requirement: `what will be saved to track if the systems 1 is working and improving the results of the main model?`. Acceptance: inspect a simulated record and confirm it contains correlation and version metadata but no raw prompt or image.
- S10 — Improvement is assessed by comparing independently judged, comparable cases with advice hidden versus shown; agreement alone does not establish benefit. Exact requirement: `something to verify if it is working and if is being improved the workflow like something if the main agent followed the instruction of the system1`. Acceptance: review an evaluation report and observe separately documented outcomes, comparison inputs, evaluator and limitations.
- S7 — Directives never grant permissions, waive a gate, or override mandatory constraints; an `absent` finding never bypasses authorization or a user-only decision. Exact requirement: `Do not grant new permissions, bypass mandatory checks, or claim authority the injection does not possess` and `Never permit an absent finding to bypass authorization or user-only decisions.` Acceptance: read an injected EXECUTION DIRECTIVES block and the AGENTS.md contract; both contain the no-new-permissions constraint and neither treats `absent` as a skip of a user-only gate.
- S8 — The existing test-permission scope is preserved. Exact requirement: `yes allow running the test, tell em if u need me to restart opencode`. Acceptance: inspect the configuration; only the named Node command is added and all prior restrictions remain.
- S11 — The adviser is governed by one checkable rules list at the repository root. Exact requirement: `i want u to create a list for this feature, place it on the root it should contain a list of things like the should help to take desicions, should obey odd workflow, should not allow uncertainability on the responses`. Acceptance: `ADVISER-RULES.md` exists at root; every rule states how it is checked; a change violating a listed rule is reported as a finding against that change, not as a style preference.
- S12 — No question carries a state its input cannot reach, and no general escape state exists. Exact requirement: `the probl;;em is taht u are allowing a fucking unknown response , all can be dropping on unknow because its too general`. Acceptance: the profile's states are reachable from the supplied input; a weak case still returns a choice plus probabilities rather than a non-answer; an existing v1 evaluation record still resolves to v1 after the bump. This supersedes nothing in S1–S11 and reverses the earlier decision (L23) that admitted `unknown` for mutual exclusivity.
- S13 — The classification eval covers both classes of every scored question, not one example of the positive. Exact requirement: `u added testing that the system one correctly land on the scope changed result is supposend u should create scenarios where is should choose that? u should not omit those tests`. Acceptance: at least four cases that must return `present` and at least four that must return `absent`, plus the same both-class coverage for `user_only_decision`, plus one case carrying an inline image for `visual_evidence: present`; the runner prints expected-class counts beside observed counts so an imbalanced set is visible; a model that answers one constant label fails on the opposite class.
- S14 — Qualifying findings inject as `=== SYSTEM 1 | EXECUTION DIRECTIVES ===` with frozen present/absent action lines; guidance requires confidence ≥ 0.60, interrupt `present` requires ≥ 0.80; `visual_evidence` absent is omitted; nothing is injected when none qualify. Exact requirement: `Keep the frozen six-action mapping in the plugin` and `If nothing qualifies, inject nothing.` Acceptance: unit tests emit the frozen action for each qualifying present/absent pair, omit below the bars and omit `visual_evidence` absent, and `formatAdvisoryBlock` returns empty when nothing qualifies.
- S15 — When that block is in the turn, System 2 must apply the findings as default workflow guidance and end the user-facing reply with one `S1 applied` / `S1 overridden` line; the line is a diagnostic clue, not proof. Exact requirement: `The persistent AGENTS.md integration contract must require System 2 to APPLY the findings, not merely report whether it applied them` and `Treat the trace as an observable diagnostic clue, not definitive proof.` Acceptance: AGENTS.md project region states both the apply duty and the one-line trace; the plugin does not duplicate that contract; tests do not claim runtime compliance.
