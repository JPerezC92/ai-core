### RC-1 — Execution result interpretation

- **Failure.** Delegates reported a successful command as having "no exit status exposed", so no verification could be recorded as passed.
- **Evidence.** The harness reports the wrapper process's status, not the inner command's. Measured 2026-11-19: `exit 7` → `Exited with code 7`; `cmd /c exit 42; exit $LASTEXITCODE` → `Exited with code 42`; `cmd /c exit 42` → `Exited with code 1`; `cmd /c exit 42; Write-Output "masked?"` → no failure line at all, with the native failure invisible. `node -e "process.exit(42)"` → `Exited with code 1`. Baseline `.aicore/core/knowledge/agents.md:48` says "Use the shell tool's captured output and exit status" without stating whose status that is, and `:47` forbids the chaining that would propagate it.
- **Root cause.** Confirmed. The shared shell-command contract does not state that the reported status belongs to the wrapper, that a native non-zero code is visible only when propagated, that a reported `1` is not the inner command's code, or that a later successful statement can mask a native failure entirely.
- **Owner.** `.aicore/core/knowledge/agents.md` `### Shell command contract`.
- **Impact.** Correct checks were reported as unverified; verification was escalated to the user instead of being resolved.
- **Correction.** State the observed semantics in the shell-command contract, and require a command whose result matters to be invoked so its own status is the one observed. Do not encode "no failure line means success".
- **Verification.** One delegate runs a passing and a failing command, plus a masked-failure probe, and reports the distinction.

- **Failure.** Capabilities were asserted and then retracted, discarding work; a claim of "no exit status exposed" in this investigation was itself an unverified capability claim.
- **Evidence.** `.aicore/core/knowledge/debt.md:44-45` (DEBT-043): three asserted integration capabilities, each retracted, each invalidating prior reasoning. The same class recurred in this investigation, where the shell tool's exit-status semantics were described before being probed.

- **Impact.** Design decisions shaped by false premises; work discarded; a delivery halted on a capability that existed.

- **Verification.** Every capability claim in the delivered work cites its probe or source revision.
- **Candidate anticipation.** The working tree's candidate `agents.md:20` already contains a capability-claim clause in this form. It is an unreviewed candidate, not accepted implementation; T1 inspects it against this root cause and retains or adapts it only if it is correct and necessary, with the retained/translated/retired accounting the rewrite rule requires.

### RC-4 — Mandatory commands without an authorized execution route

- **Failure.** A runtime declares a command mandatory that no effective grant authorizes, so a mandatory control is permanently unavailable while documents read as satisfied.
- **Evidence.** `.aicore/core/knowledge/debt.md:126-133` (DEBT-058), including recurrence on 2026-11-18 where Forge's autofix route and Crucible's review-suite route were both ungranted. Baseline instance: `.opencode/opencode.jsonc:24` denies Crucible all shell by default and grants exact forms, and the two granted ODD-validator forms named the P7 record (`opencode.jsonc:78`) and `odd/features/architecture-contract.md` (`opencode.jsonc:83`) — no baseline form authorized validating any other record. Baseline `.opencode/agents/crucible.md:202` states the consequence in the runtime itself: "the validator forms name the two documents of one specific change record, so a later validator need requires its own exact form rather than a widened pattern".
- **Root cause.** Confirmed. No check reconciles a runtime's declared mandatory commands against the effective rules, and the per-record exact-form model makes every new record require a new grant.
- **Owner.** `.opencode/opencode.jsonc` grants together with the runtime text that names the mandatory command; DEBT-058 is the register entry.
- **Impact.** A required verification cannot be executed by the role assigned to perform it; review rounds repeat because the reviewer cannot run what it must verify.
- **Correction.** Implement DEBT-058's already-specified static reconciliation over runtime text and harness configuration — no second permission engine — and give the reviewer a validation route that does not depend on a new grant per record.
- **Sustainable alignment.** Detection alone is not sufficient: a check that reports a conflict after every new record is created still leaves the same manual grant edit each time. The correction therefore has two parts. The reconciliation detects the conflict, and the grant model stops being record-specific. A reviewer validates any record in a directory through one exact, directory-scoped form — `node .agents/skills/odd-workflow/scripts/validate_feature.ts odd/tasks` and `node .agents/skills/odd-workflow/scripts/validate_feature_file.ts odd/features` — instead of one exact form per record path. The scope is bounded by the exact command text and the two directories it names, so it is wider than a single-record form but far narrower than a wildcard, and it grants no interpreter, install, network, Git/GitHub or destructive authority. Where a duty genuinely needs a narrower path than the directory form, that narrower form stays exact and is justified in the runtime text; the per-record grant is then the exception rather than the routine. Deny-by-default is preserved: the roles' global shell deny, the exact-form matching and the no-Git/GitHub boundary are unchanged, and adding the directory-scoped validator forms does not make any other command reachable. The directory-scoped grant is a bounded permission change the user directed to be evaluated under the PR 1 implementation authorization, with its effective behavior verified by literal probe after a harness reload and deny-by-default preserved.
- **Verification.** The reconciliation reports every declared mandatory command and its effective allow or deny, fails closed on a deliberately misaligned fixture, and passes on the corrected tree; a new change record is then created and validated through the directory-scoped form with no grant edit, confirming that alignment no longer requires per-record grants; runtime behavior is evidenced separately by literal probes.
- **Candidate anticipation.** The working tree's candidate `opencode.jsonc:93` and `:98` add two further **per-record** validator forms — one for this record and one for `odd/features/agent-execution-permissions.md` — and the candidate `crucible.md:209` extends the same per-record pattern. Those candidates were written against the earlier narrow objective and move the grant model in the opposite direction from the sustainable alignment above. T1 inspects each against this root cause, retains or adapts only what is correct and necessary, and the directory-scoped form is what supersedes the per-record ones.

The refusal and the divergent second outcome are recorded in this investigation.

- **Impact.** Review blocks on evidence it cannot reach; the same input yields divergent verdicts; verification repeats.

- **Verification.** Dispatch the designated reviewer with the baseline at an in-scope path; it reads the complete file and binds its verdict to both content identities.
- **Candidate anticipation.** The working tree's candidate `agents.md:73` already contains both clauses this root cause names — the reviewer-accessible destination requirement and the complete, identity-verified delivery requirement. It is an unreviewed candidate, not accepted implementation; T1 inspects it against this root cause and retains or adapts it only if it is correct and necessary, with the retained/translated/retired accounting the rewrite rule requires.

### RC-7 — Requirements-driven testing and existing ODD acceptance enforcement

- **Failure.** Test coverage accumulated without a governing requirement behind it, historical compatibility examples were treated as mandatory individual requirements, and whole-feature acceptance could be reported without per-spec verdicts or commit-bound evidence.
- **Evidence.** `.aicore/core/knowledge/debt.md:148-150` (DEBT-060) records requirement erosion and suite growth without simplification. `odd/features/organic-driven-development.md` R7 (evidence bound to its commit), R8 (the first failure recorded) and R12 (an independent reviewer's verdict recorded per requirement) are unticked. The existing validator (`.agents/skills/odd-workflow/scripts/feature_validation/domain/rules.ts:235-400`) checks anatomy only and verifies neither per-spec verdicts nor commit-bound evidence, so the requirement exists in the workflow and the durable feature while nothing observes it at close.
- **Root cause.** Confirmed. The requirements are stated; the enforcement point is missing. The testing contract already owns the level boundaries (`.aicore/core/architecture/testing/architecture.md` T2, T4, T5, T8), so the gap is not in the contract's content but in how the change record's delivered evidence and its close are checked against it.
- **Owner.** `.agents/skills/odd-workflow/SKILL.md` and the existing validators in `.agents/skills/odd-workflow/scripts/`.
- **Impact.** A green suite and an aggregate verdict can stand in for acceptance; a requirement can be lost between original and delivered without detection; a historical example can harden into a permanent test obligation.
- **Correction.** Make the existing close and the existing validator observe the existing requirements: the independent review returns a verdict per `S#`, a closed record carries those per-spec verdicts, commit-bound evidence and the first-failure record, and delivered test coverage is traceable to the governing requirements at the boundary the testing contract assigns. No new approval stage, no duplicate acceptance gate, no one-to-one requirement-to-test mapping and no additional per-test artifact is introduced, and the suite grows only where a governing requirement requires it.
- **Enforcement shape.** The shape is the one the ODD skill already defines, not a new one. `.agents/skills/odd-workflow/SKILL.md:159` already requires the independent verification handoff to "retain the returned per-spec verdicts and missing checks in the existing Log", and the skill's `### Close` already requires zero open findings before a clean completion claim. The missing enforcement is that nothing observes those per-spec verdicts at close: the validator checks anatomy only. The correction therefore makes the existing validator check the existing shape — that a closed record's Log carries a verdict for each of its `S#` entries together with a pointer to the durable source holding the evidence, that each recorded evidence entry names the commit it ran against, and that a record with an applicable executable failure records it — reusing the Log's existing entry format rather than adding a second tracker. The durable feature `odd/features/organic-driven-development.md` is the owner of the requirement text; R7, R8 and R12 are the affected requirements, and only the delivering change may tick them.
- **Validator compatibility.** The new closure rules apply prospectively and do not retroactively invalidate accepted history. The existing validator already separates the two populations through its effective-date rule (`feature_validation/domain/rules.ts:22`, `CLOSURE_CONSISTENCY_EFFECTIVE_FROM`), and the closure rules extend that same mechanism rather than introducing a second one: records created before the rules' effective date keep their existing status, Log and Specs exactly as written, and are never re-validated against a rule they predate. The first-failure record is required only where an executable failure applies, matching the existing wording of `odd/features/organic-driven-development.md` R8, which already permits stating the reason an executable failure cannot apply instead of recording a failure. A record is never made to satisfy a new rule by fabricated or back-dated evidence.
- **Verification.** The existing validator rejects a closed-shape record lacking per-spec verdicts and commit-bound evidence, accepts a compliant one, and keeps its other contracts unchanged; a pre-effective-date record keeps its existing status and Log unchanged under the new rules; and a record with no applicable executable failure is accepted when it states the reason.

### RC-8 — Invalid PR creation bodies

- **Failure.** A pull request was published whose `## Findings / blockers` section the canonical body validator rejects; every later validation failed on the published baseline, and the delivery required a replacement pull request.
- **Evidence.** `odd/tasks/2026-11-18-p7-system-one-odd-adviser-test-remediation.md:463` (L31/L32) records the body shape and the resulting `BODY_INVALID`. The code path: `.agents/skills/git-pr/scripts/pr_content/application/initialize_working_body.ts:24-29` calls only `extractBody` (`domain/body_validation.ts:43-49`), which checks the title wrapper and that the body starts with `## Summary`; the canonical structural rules live in `validateBody` (`domain/body_validation.ts:110-139`) and are reached only through `validate`, which runs after creation (`.agents/skills/git-pr-workflow/SKILL.md:29-36`). The skill text calls `initialize` "the one authoritative rejection point for a malformed creation draft" (`:31`), so the code is narrower than the stated contract.
- **Root cause.** Confirmed. The creation path has no structural rejection, while the contract asserts one. The pre-publication path (`validate`) does apply the canonical rules, but it runs after the pull request exists, so it can only prevent a bad later body update and cannot prevent the initial creation.
- **Owner.** `.agents/skills/git-pr/scripts/pr_content/` — `application/initialize_working_body.ts` and `domain/body_validation.ts`.
- **Impact.** An invalid published body becomes its own invalid preservation baseline and cannot be repaired in place, forcing replacement pull requests.
- **Correction.** Reuse the existing canonical parser inside the creation path so a malformed draft is refused before anything is published, and keep the pre-publication validation that already precedes a body update. The code is corrected to match the stated contract; relaxing the contract text so the creation path accepts a malformed body is not an available outcome, because a pull request that already exists cannot be un-created by its own tooling.
- **Verification.** A creation draft whose findings section carries the placeholder followed by prose is refused and creates no working body; a compliant draft produces one; the pre-publication rejection of an invalid candidate body still holds.

### RC-9 — Authorized protected-content supersession

- **Failure.** A published `## Summary` stated a decision premise the user later superseded, and no supported route existed to correct it, so the delivery could only be replaced.
- **Evidence.** `.agents/skills/git-pr/scripts/pr_content/domain/review_content_preservation.ts:23-25` requires `Summary` and `Breaking changes` byte-equality with the accepted baseline and `application/validate_final_body.ts:32-33` applies it unconditionally; `domain/review_decisions.ts:47-69` parses acceptance evidence that reaches only `validateBody`, never preservation. `.aicore/core/knowledge/debt.md:151-159` (DEBT-060) records the recurrence and the resulting replacement-pull-request cycle.
- **Root cause.** Confirmed. A user-authorized change to a protected section has no authorized representation.
- **Owner.** `.agents/skills/git-pr/scripts/pr_content/domain/review_content_preservation.ts` and `domain/review_decisions.ts`.
- **Impact.** Published text can contradict the user's accepted decision, and correcting it costs a replacement pull request.
- **Correction.** Provide a supersession mechanism whose authorization is explicit, attributable and independently verifiable, which preserves every other protected section unchanged. GitHub's content-protection guarantees are preserved: preservation is not bypassed, and the mechanism's implementation shape is an engineering choice for the owning agent (see `### Repository-determined choices`).
- **Verification.** An authorized protected-section change is accepted through that route and published with all other protected content unchanged; an unauthorized change to the same section is refused; the accepting authority is independently verifiable from the persisted evidence.

### RC-10 — PR artifact identity and isolation

- **Failure.** Preparation artifacts for different pull requests share fixed paths, so one context can silently replace another's.
- **Evidence.** `.aicore/core/knowledge/debt.md:137-143` (DEBT-059) records the recovery of PR #197 and the shared-path hazard; `.agents/skills/git-pr/SKILL.md:86` fixes the draft at `output/pr-draft.md` and the working body at `output/pr-working-body.md`.
- **Root cause.** Confirmed. No per-context artifact location or association exists.
- **Owner.** `.agents/skills/git-pr/SKILL.md` and `.agents/skills/git-pr-workflow/SKILL.md`.
- **Impact.** A draft can be overwritten by another context; evidence provenance becomes ambiguous.
- **Correction.** Establish identifiable, isolated artifact locations per pull-request context, with unambiguous association to their owner, preserving the canonical writer and Git-authority boundaries.
- **Verification.** Two concurrent preparation contexts use distinct locations, and each artifact resolves to its own context.

### RC-12 — Accurate delivery and lifecycle reporting

- **Failure.** Work that had reached only analysis or planning was reported in language that could be read as delivery.
- **Evidence.** `.aicore/core/knowledge/debt.md:145-159` (DEBT-060) records repeated interruption and misreported state across P7 and PR #199–#203. `.agents/skills/odd-workflow/SKILL.md:169` (`### Completion stages`) already orders implementation, verification, publication, closure, merge and cleanup, and `.aicore/core/knowledge/agents.md:201` already reserves `ALL FINISHED` for a closed record — but neither requires a report to name the stage it reached.
- **Root cause.** Confirmed. The vocabulary exists; the reporting obligation does not.
- **Owner.** `.aicore/core/knowledge/agents.md` `### Message presentation`.
- **Impact.** A pull request appears merge-ready while its record is not closed; planning reads as delivery.
- **Correction.** Require a status report to name the stage reached and, when it cannot, the stage not reached and why. No new status vocabulary.
- **Verification.** A delivery report names its stage and matches the actual repository and pull-request state.

## End-to-end acceptance scenario

One representative authorized change, of the kind that has failed before, is executed end to end under the corrected workflow using the existing mechanisms. No simulation framework is built and no pull request is published by the scenario itself.

1. **Requirements.** The change states its requirements as behavioral `S#` entries, each naming the observable outcome and its acceptance. A historical compatibility example does not become a requirement unless a governing spec or an accepted user decision states it as such.
2. **Orchestration and delegation.** The coordinator reconstructs the actual state and authorized scope, then dispatches each task with its objective, canonical references, restrictions, inputs, required executable actions, acceptance criteria and the execution route the delegate's effective rules permit. The delegate receives no copy of the whole record; it reads the canonical source.
3. **Execution readiness.** Every command the dispatch requires resolves to an allow for that delegate, proven by the static reconciliation and, where runtime behavior matters, by a literal probe from that delegate's own shell. A prohibited operation is refused.
4. **Implementation.** The implementer works only within the assigned paths and returns attributable evidence.
5. **Testing.** Delivered coverage is traceable to the governing requirements and sits at the level the testing contract assigns, with no case present solely because a historical example existed.
6. **Independent review.** The reviewer receives the original and candidate at a path its runtime permits it to read, complete and identity-bound, and returns a verdict per `S#` together with the original-obligation accounting.
7. **Pull-request preparation.** The creation draft is refused if the canonical parser would reject it, a valid draft produces a publishable body, an invalid candidate body is refused before any body publication, artifacts are isolated to that context, and a later authorized protected-section correction is applied through the supersession mechanism with every other protected section unchanged. This is a controlled pre-publication verification: no pull request is created and no live body is published.
8. **Completion reporting.** The report names the stage reached and the stage not reached, and each named stage matches the actual repository state.

No stage may be reported as reached on the strength of a plan, an analysis, or a stated intent.
