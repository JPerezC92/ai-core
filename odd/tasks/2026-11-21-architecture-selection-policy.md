## Specs

- S1 — Complexity selection is evidence-based and no count or project type selects a level. Exact requirement: "Line count alone must not determine architecture." / "Number of files alone must not determine architecture." / "A project type alone must not automatically force L3." / "Adding an external dependency does not automatically require a repository abstraction." / "A pure helper does not require a use-case class." / "Existing repositories must retain their approved architecture unless migration is separately authorized." Acceptance: read the level-selection rule in the common architecture contract and confirm all six prohibitions are stated and no line-count, file-count or project-type criterion selects a level; every prohibition is present and no counting rule appears.

- S2 — One material architectural boundary is sufficient to justify L3, with no numeric threshold. Exact requirement: "Do not require two or more qualifying signals. One sufficiently important architectural boundary may justify L3. Use evidence-based judgment rather than mechanical thresholds." Acceptance: read the selection criteria; a single qualifying boundary is stated as sufficient and no minimum count, score or ratio appears.

- S3 — L1 requires no Clean Architecture layout or artificial operation class, and external-effect count is not a criterion. Exact requirement: "No mandatory Clean Architecture directories." / "Do not impose class-based use cases unnecessarily." / "L1 must be determined by responsibility complexity and architectural needs, not the number of filesystem, process, or network operations." Acceptance: read the L1 clause and the excluded-signal list; the L1 clause mandates no layout and no class, and the number of filesystem, process or network operations appears only as an excluded signal.

- S4 — L3 retains class, single `execute()` and constructor injection, and the amendment is prospective and historically accurate. Exact requirement: "Preserve the class + `execute()` convention for formal L3 use cases." / "The effective date of the C3 amendment must reflect the actual acceptance of the new architectural decision. Do not retroactively declare the new rule effective before acceptance." / "Do not imply the 2026-11-12 decision was originally limited to L3." Acceptance: read the operation rule and the amendment records; the L3 class form is stated, the amendment record states the prior requirement was universal until this change, and its effective date is the recorded acceptance date rather than an earlier one.

- S5 — The Interface responsibility exists wherever an external entry boundary exists, and its own directory is optional. Exact requirement: "The Interface responsibility exists when an external entry boundary exists, but extracting it into a separate `interfaces/` directory is optional." / "Use `interfaces/` as the canonical name when an independent Interface directory is explicitly authorized." Acceptance: read the Interface-boundary rules; existence and optionality are separate statements and `interfaces/` is named as the canonical directory for an authorized extraction.

- S6 — Interface handlers delegate business behavior and are not required to call exactly one operation. Exact requirement: "Do not require exactly one application operation per handler in every situation. Explain how orchestration should be handled without duplicating business coordination inside interfaces." Acceptance: read the delegation rule; it permits one or several operations per handler and states when a sequence must become an operation rather than remain in the handler.

- S7 — At L3, interface modules and infrastructure adapters stay independent before and after extraction, and extraction may not pretext a redesign. Exact requirement: "For L3, Interface modules and Infrastructure adapters must remain independent outer boundaries, even before physical extraction." / "extraction must never be used as a pretext for an unrelated domain/application redesign." Acceptance: read the placement rule; co-located independence is stated, and redesigning domain or application to enable an extraction is expressly excluded.

- S8 — Import rules constrain architectural dependencies, not legitimate external libraries. Exact requirement: "The L3 import restrictions must govern dependencies between architectural components, not prohibit legitimate external libraries." / "Interface modules may use their own transport frameworks and SDKs." / "Infrastructure adapters may use external clients, drivers, and internal infrastructure utilities." Acceptance: read the dependency rule; transport frameworks, SDKs, clients and drivers are explicitly permitted and only edges between architectural components are constrained.

- S9 — L1/L2 responsibility separation creates no mandatory extra files, classes or wrappers. Exact requirement: "Do not turn L1/L2 responsibility separation into mandatory extra files, classes, or wrapper functions for trivial scripts." Acceptance: read the L1/L2 Interface clause; it requires no additional file, class or wrapper and states no inversion, port or adapter requirement.

- S10 — Pure rules and transformations are approved unit-test targets without per-file obligation or added infrastructure. Exact requirement: "Prefer Option A — allow unit testing of pure rules and transformations, without creating a per-file testing obligation." / "Do not require one test file per function, and do not make trivial utilities require additional test infrastructure." Acceptance: read the testing contract's approved-target rule; the pure rule or transformation is an approved target, and both the per-file obligation and any additional infrastructure or runner requirement are expressly excluded.

- S11 — Architecture records are required only for genuine project-level decisions. Exact requirement: "Architecture classification must not require creating new documentation for every small L1 script or utility." / "Require formal architecture records when justified by project-level architectural decisions, especially for L3". Acceptance: read the recording clause; an L1 classification requires no record and the record duty is limited to project-level architectural decisions and changes to an approved architecture.

- S12 — The circular diagram represents L3 only, and the dependency diagrams separate allowed from required dependencies. Exact requirement: "The circular SVG must explicitly represent L3 Clean Architecture only. L1 and L2 must not inherit mandatory layer directories from the diagram." / "Architecture diagrams must distinguish allowed dependencies from required dependencies. Do not imply that infrastructure adapters must import Application." Acceptance: view the diagram section; the circular figure is labelled L3-only and the deployment figures mark inward dependencies as permitted without marking any edge as required between the two outer boundaries.

- S13 — Normative rules live in the common architecture contract and are mapped by shapes and guides. Exact requirement: "Preserve Decision 2 Option A as the preferred design: normative rules in the common contract, referenced by shapes and guides." Acceptance: read the common contract and the three implementation guides; the new rules carry identifiers in the common contract and each applicable guide maps every one of them.

- S14 — The change introduces no migration, no enforcement tooling and no conformance claim. Exact requirement: "Do not migrate existing project structures or add enforcement tooling as part of this documentation work." / "Do not claim existing implementations conform unless supported by evidence." Acceptance: inspect the committed change set; no production source, dependency, configuration, clearance or tooling path changed, and no delivered statement asserts that an existing implementation conforms.

- S15 — The change stays inside the approved documentation inventory. Exact requirement: "Implement only the approved documentation changes within the 23-file inventory." Acceptance: inspect the committed change set; every touched path is one of the approved inventory paths and no other path changed.

- S16 — Agents have one ordered decision procedure, and the levels are not sequential stages. Exact requirement: "Agents must follow this sequence: 1. Identify whether the task belongs to an existing project or a new project. 2. Read the project's approved architecture and applicable AICore contracts. 3. Identify responsibilities, external boundaries, and consumers. 4. Evaluate architecture complexity and choose L1/L2/L3 only when the selection is not already fixed. 5. Select the applicable application shape. 6. Determine whether interface responsibilities exist. 7. Place interface code according to the chosen shape and approved structure. 8. Prevent business and transport responsibilities from mixing. 9. Validate dependency boundaries with focused, proportionate checks. 10. Document any proposed deviation and request approval before changing architectural conventions." / "Agents must not interpret L1, L2, and L3 as mandatory sequential stages." Acceptance: read the selection procedure; all ten steps appear in the stated order and the non-sequential statement is present.
