## Specs

- S1 — `testing-architecture/architecture.md` is the single language-agnostic test-architecture contract. It defines the test levels in terms of clean-architecture boundaries, behavior isolation, factory data, one mocking library, one behavior per module or class, test organization, and the rule that a passing execution never establishes architecture conformance. It contains no language-specific runner, framework, or path convention. The dedicated `testing-architecture/` area keeps this rulebook distinct from `knowledge/` registers and policies.
- S2 — `testing-architecture/stacks/typescript.md` is the first derived stack guide, uses `testing-architecture/stacks/_template.md`, and preserves every current TypeScript rule from `.opencode/agents/crucible.md` `#### TypeScript`: the backend/frontend pyramid, Vitest unit and integration rules, supertest end-to-end rules, Playwright three-phase rules, hook-plus-component testing, mock-at-service-never-hook, `MockProxy`, `renderWithQueryClient`, screen assertions, factories, parser tests, and shared tooling consistency. It is the reference depth for every later stack guide. No rule is weakened, invented, or silently retired.
- S3 — `testing-architecture/stacks/python.md` is the Python-plus-pytest derived guide and preserves every current Python rule from `.opencode/agents/crucible.md` `#### Python`: the same three levels, project-wide pytest discovery, `test_*.py` naming, function or non-`TestCase` classes, no `unittest.TestCase` or `unittest.main`, allowed `unittest.mock`, hermetic `tmp_path` fixtures, direct `assert` and `pytest.raises`, and feature-spec happy/rejection traceability. It must reach the same structural depth as the TypeScript guide: the same heading order and rule granularity, a concrete Python pyramid mapping, file-organization rules, doubles and factory guidance, runner/tool ownership, and explicit `N/A` reasons where a TypeScript frontend or framework rule has no Python analogue. Python rules are derived from current repository evidence and the agnostic contract, not copied mechanically from TypeScript; runner selection remains project-owned.
- S4 — `testing-architecture/stacks/_template.md` is the single template for future stack guides. It requires applicability, stack and tooling ownership, mapping to the agnostic levels, file organization, concrete rules, test data and doubles, execution and selection, evidence, and open decisions. It includes a section-parity checklist: every section is either completed or explicitly marked not applicable with a reason; a stack guide is never accepted with an implicit or thin section. A new guide remains `proposed` until reviewed; it requires official-documentation research and repository inspection, and it must never invent a runner or rule.
- S5 — `.opencode/agents/crucible.md` reads the agnostic contract first, then the applicable stack guide. It retains review scope and snapshot, test execution, dependency-install workflow, the no-Git boundary, source neutrality, output format, and stop-and-report behavior. It routes `.ts`/`.tsx` files to the TypeScript guide and Python `test_*.py` files to the Python guide. An unlisted stack returns `[UNCERTAIN]` and reports the missing guide rather than guessing. The spec contains no full stack-specific rulebook. The spec advances by minor SemVer and the source-version contract fixture is updated with it.
- S6 — `knowledge/agents.md` `### Clean architecture (language-agnostic) (HARD RULE)` no longer duplicates the full test-level contract; it points to `testing-architecture/architecture.md` while retaining every non-test clean-architecture obligation. Every original test-level obligation is retained in the agnostic guide.
- S7 — `docs/architecture/decisions/0002-testing-architecture-layering.md` records the context, decision, alternatives, consequences, and the process for adding future stack guides. The ADR is source-local and preserves the user's existing pyramid decisions rather than reopening them.
- S8 — The new shared documents are cleared for distribution in `distribution-clearance.json`; `distribution-clearance.definition.md` describes their distribution class; `README.md` lists them; `AGENTS.md` and the README reuse guidance no longer describe `crucible.md` as the whole test rulebook. No destination-specific tool binding is presented as universal.
- S9 — Original/candidate accounting proves every existing test-architecture obligation is retained, translated, or explicitly retired with authority. No behavior or tooling mandate changes. The agnostic guide contains zero stack-specific runner or framework names; stack guides are clearly labeled reference implementations, not destination bindings. The Python guide is reviewed against the TypeScript guide section by section, with every difference justified by Python semantics or an explicit `N/A` reason; a shorter or less specific Python guide is a defect.
- S10 — Verification covers link resolution, required core/project markers, clearance JSON parsing, the feature validator, the whole suite, and an independent Sentinel 🛡️ (Quality Guardian) audit. No dependency, permission, plugin, context-injection, or destination change is introduced.
- S11 — Cross-stack parity is a first-class requirement. Every stack guide follows the same template and parity checklist; `testing-architecture/architecture.md` carries a stack-guide index with applicability, status, scope, and parity-review evidence. Differences between guides are allowed only for language or runtime semantics and must be declared; a missing section, a less specific rule, or a thin inherited section is a defect. A new language is not approved until the same parity review passes.
