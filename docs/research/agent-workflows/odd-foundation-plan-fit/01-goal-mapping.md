# 01 — Goal mapping: G1, G2, G3

> Part of the ODD fit publication ([`README.md`](README.md)). Source: `output/research/odd-foundation-fit/brief.md`, Q1–Q3. Citation convention: `S#` = research-set citation IDs; plan passages cited by section name + goal/row identity; every mapping judgment keeps its `infer:` label. Verdict vocabulary: strong / partial / none / conflict. Nothing here authorizes anything or claims a plan goal met.

## G1 — discoverable entry point and defined homes (brief Q1)

- **Entry model — partial-to-strong fit (mechanism differs).** `infer:` ODD's entry is *implicit and harness-injected*: "ODD runs by default on every request, in every configured runtime, without you asking for a workflow, a plan, or task tracking" (S4). The plan's entry is *explicit and prose-enforced*: "Root instructions explicitly require reading the entry" (plan, Goals G1, Done when). The shared property is "no request proceeds without the workflow applying"; the delivery mechanism is different. **Downgrade:** a required-read pointer cannot replicate true default-on behavior without the harness binary — that is a real gap, not a cosmetic one (see [`README.md`](README.md) gap 1).
- **"Load applicable instructions and relevant dependencies" (plan, Approved foundation contract) — partial-to-strong.** ODD's handoff rule — "workers receive a reference to the document, their task, and its `S#`, never a paraphrase of your request; they read until `## Log`" (S4) — is the same reference-not-paraphrase discipline. `infer:` "Project-local skills win over same-name global skills" and multi-root skill discovery (S4) supply a concrete precedence precedent for the plan's "Find the governing source" routing and "one canonical owner per concern" (plan, Goals G2, How).
- **`odd/tasks/` as a home lesson — strong on the principle, partial on the scheme.** The feature document has one fixed anatomy and one home (header / `## Specs` with verbatim-quoted numbered requirements / `## Tasks` one line per task / `## Log` with `L1` = the user's original request verbatim) (S4). The requirement-change rule — "A requirement change rewrites only the affected spec and reopens only its task" (S4) — is the strongest single lesson for the plan's Migration acceptance ("Move each obligation to exactly one authoritative home", plan, Migration acceptance) and its "New files require a distinct responsibility and owner, not just a convenient empty directory" (plan, Target structure placement rules). `infer:` the scheme itself does **not** transfer: ODD's home is one *per-feature* living document mixing spec, tasks and execution log; the plan demands one home *per responsibility* with separated promises/constraints/Proof/history (plan, Stage C) and forbids accumulating "running execution transcripts" (plan, Small-document budgets). See [`03-conflicts-and-guardrails.md`](03-conflicts-and-guardrails.md), conflict 7.

## G2 — critical assessment, conflict reporting, no silent widening (brief Q2)

- **Step 1 Authorize — strong.** "does the request authorize a change? read-only work stays read-only" (S4); "findings do not silently expand authorization" (S5) maps directly to G2's "without silently widening work" (plan, Goals G2) and "fix only authorized in-scope issues" (plan, For encountered defects).
- **Step 3 one focused question — strong for the question-routing tension.** "one focused question for a real decision", at most one assumption challenge for a high-consequence unproven premise (S4); "Only real unresolved product decisions prompt a focused user question, one at a time with a stop/wait; delegated workers return gaps to the parent rather than assume choices" (S4). `infer:` this gives the plan's "narrow clarification of question routing… consistently with existing evidence-first, user-only decision routing" (plan, Approved foundation contract; tension recorded at plan, Evidence inspected and limits, `AGENTS.md` row = "question-routing tension") an operational test: ask only for a real unresolved product decision, one at a time, with stop/wait; everything else returns as a gap, not a guess. Partial caveat: ODD's rule is role-agnostic, while the plan keeps question authority user-only via Cipher 🔓 (Lead Orchestrator) — the rule narrows *when* to ask, not *who* may ask.
- **Delegation trigger rule — partial (principle transfers, target differs).** "A trigger holds only when its condition truly holds; none holds by default… File count, task size, or a model price ratio never decide the route on their own" (S9). `infer:` the transferable principle is "conditions hold or the default (no action) stands", which maps to the plan's "An unresolved finding reported for later consideration is not automatically accepted nonblocking debt" (plan, For encountered defects) — neither auto-block nor auto-defer. Weakness: the rule governs delegation routing, not conflict disposition; the mapping is analogical, not literal.
- **RDD causal admission — strong, with a guardrail.** "a finding can only block your change if YOUR change caused it" (S8) maps to "route unrelated issues to the existing owner/register with the required explicit deferral" (plan, For encountered defects) and the scenario "an unrelated pre-existing defect" (plan, Verification, Scenario review). Guardrail (`infer:`): the plan's stop triggers — "unmet selected requirements, safety/authority conflicts, or necessary scope changes" (plan, For encountered defects) — are authority-based, not causal; a literal causal-admission rule would wrongly defer a safety/authority conflict the change did not cause. Any adoption must state this subordination explicitly. See [`03-conflicts-and-guardrails.md`](03-conflicts-and-guardrails.md), conflict 5(d).

## G3 — verifiable and distributable (brief Q3)

- **Close discipline — strong.** "report the verified outcome, every failed or pending check, and the next step" (S4) maps to the ordinary envelope "result/status → governing source and observed evidence → impact/scope → recommendation/next action → decision needed (`none` when factual)" (plan, Approved foundation contract), and "a reported failure is reproduced before anyone decides it already works" (S4) maps to "Distinguish constructed examples from observed live runs" (plan, Verification) and R4's "expected and observed verdicts… walkthroughs are labelled" (plan, R4, Done when).
- **"Prose alone is not proof" — strong.** "Good human decisions do not survive contact with an agent unless something enforces them" (S7) is a near-exact restatement of G3's Issue: "an ADR or new prose alone cannot prove reliable future execution" (plan, Goals G3). `infer:` both argue for mechanism-backed verification over attestation.
- **Distribution — none.** ODD's only distribution mechanism is the Engram topic mirror `odd/<feature-name>/tasks` (S4), with a documented non-atomic-write caveat ("Read back both writes: they are not atomic", S4). It has no counterpart to the plan's region clearance, `distribution-clearance.json` rows, source-neutrality and portable-set review (plan, Goals G3, Verification, Portable-set review). `infer:` on distribution, ODD contributes nothing; the plan's model is stricter and self-standing.
