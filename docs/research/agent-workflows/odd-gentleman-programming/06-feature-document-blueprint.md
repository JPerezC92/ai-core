## Scope and evidence boundaries

The release page identifies gentle-ai v4.3.1, dated 2026-10-27, at commit `2dba7784114fff57864519c4c0d067e952a8c98b` (S30). The inspected `docs/usage.md` and `docs/intended-usage.md` were fetched from paths at that commit, but each says it tracks `main` and links to v4.0.0 documentation (S31, S32). A pinned retrieval identifies the bytes inspected; it does **not** make those pages release-specific documentation.

This chapter separates five kinds of evidence:

1. **Formal prose** describes the workflow and feature-file sections (S31, S32).
2. **Rendered routing guidance** is text generated by the canonical non-Pi renderer (S33); Pi has a separate ODD step sequence and integration guidance (S33, S34).
3. **Tests and fixtures** show what selected renderer tests assert, not that arbitrary documents are valid or that a model complied (S35).
4. **Repository examples and inventory** show what selected files contain and what the bounded tree/heading scan counted (S36, S37).
5. **The supplied video transcript** is version/date-unknown narration and demonstration, not a release-specific specification (S38).

## Blueprint stated by the formal prose

The formal usage prose describes this order: a short header, numbered `## Specs`, one-line entries under `## Tasks`, and `## Log` last (S31). The header is short; the prose does not establish one universal set of header headings. Rendered non-Pi guidance elaborates the header as 2–3 lines for objective, branch, delivery strategy, and test runner (S33). Treat that elaboration as renderer guidance, not a requirement that every repository example use identical labels.

### `## Specs`

Specs are numbered requirements. The prose calls for verbatim requirements, including exact strings, error messages, or examples where applicable, together with acceptance criteria and checks (S31). It keeps requirement text in the Specs section and acceptance criteria/checks alongside those requirements. The pinned compact examples use a `Specs` section (S36); their wording remains example content, not additional universal schema.

### `## Tasks`

The prose specifies one line per task, carrying a stable task ID, a linked spec, a route, and a commit reference (S31). Rendered routing adds task-status and commit or RED/GREEN evidence details (S33). These are guidance about tracking progress and linking work to requirements; they do not prove that the renderer validates a hand-written task file.

### `## Log`

The prose places `## Log` last: `L1` records the original request verbatim, and later entries append corrections, evidence, and rationale (S31). It is a chronological record of source material and decisions, not a license to promote every example's fields into a required log schema.

### What the repository examples do—and do not—establish

At the pinned commit, `odd/tasks/odd-spec-by-reference.md` and `odd/tasks/task-size-canon.md` are compact examples with `Specs`, `Tasks`, and `Log`. `odd/tasks/odd-mandatory-delegation.md` uses a different, older Objective/Problem/Scope/Outcome-style layout (S36). The latter is evidence that a real file used those headings; it is **not** evidence that those headings are required by the current prose. In the bounded recursive tree inventory, 53 `odd/tasks/*.md` paths were found, and an exact-heading scan found 16 with all three `Specs`/`Tasks`/`Log` headings (S37). These counts describe that scan only; they are not a complete repository-content or validator audit.

## Renderer and progress details

`RenderRouting` is the canonical non-Pi renderer inspected here. Its output elaborates task status, commit linkage, and RED/GREEN evidence, and contains mandatory-delegation guidance (S33). Named tests check organic task continuity, work-unit commit/review wording, mandatory delegation wording, and a usage-guide description of the by-reference feature document. Golden tests compare rendered output with fixtures (S35). These tests establish assertions about rendered text/bytes. They do not establish arbitrary feature-file schema validation, runtime parity, or model compliance.

The Pi path is distinct: the source contains separate `piODDSteps`, and the Pi integration documentation and routing fixture are separate evidence (S33, S34, S35). Do not infer identical rendered wording or behavior across non-Pi and Pi from one renderer or fixture; no full Gentle Shell/runtime execution was part of this evidence set.

The transcript's feature-file example (20:45–22:24) and its particular fields/phases are demonstrations, not a universal schema. Its visual/golden-file evidence is likewise a demonstrated evidence format, not a requirement that every task produce visual goldens. The video also demonstrates a diagnosis → uncertainty resolution → writer sequence (23:07–23:45) and chained/direct PR strategies (36:34–37:31) (S38). None of these establishes universal ODD phases, task fields, or delivery choices. The formal prose and renderer provide the documented guidance; the video does not amend it.

## Two distinct uses of “about 400 lines”

The delivery forecast is based on authored additions plus deletions, excluding generated files. The guidance calls for a running count and a delivery strategy when the forecast/count exceeds about 400 lines (S31, S33). Separately, the task-level ~400-authored-line figure is an advisory planning heuristic. It is not a hard cap, forced split, acceptance criterion, or RDD trigger (S31; historical v4.2.0 prose also says this in S4). Do not collapse the delivery forecast and task-size heuristic into one rule.

The transcript's discussion of “400 lines” at 29:21–30:47 is a demonstration and is not used to override the prose's separate meanings (S38). The transcript's RDD-default statement is also version/date-unknown. The available evidence does not reconcile that narration with the current-document and historical-version accounts; do not retrofit the video's claim to v4.3.1 or call the inspected usage pages release-specific (S4, S31, S38).
