# ADR 0005 — Use-case organization and naming

- **Status:** Proposed — pending review and explicit approval
- **Date:** 2026-10-29

## Context

C3 already fixes the semantic unit: "Each use case is one named business operation exposing a single `execute()`" ([`architecture/clean-architecture.md`](../../../architecture/clean-architecture.md) → `C3 — Application operation`). The accepted backend shape already requires `application/` with one file per use case ([`architecture/shapes/backend.md`](../../../architecture/shapes/backend.md) → `B1 — Layout and domain`), the NestJS guide already requires `application/use-cases/` with a pure class exposing one `execute()`, and the Python guide already requires "the module holding the named `execute()` operation" with "one named operation". What was not yet fixed before this decision was the **naming pattern** and the boundary between an operation and the composition code that calls it.

The durable research record [`anemic-domain-model-and-use-case-naming`](../../research/architecture/anemic-domain-model-and-use-case-naming/README.md) (2026-10-28) supplies the naming evidence:

- A use-case name is the goal as an active verb phrase; commands should name business tasks, not data updates.
- `Service` names a layer or grouping, `Manager`/`Helper`/`Processor`/`Util` name a mechanism or a vague role; none is intention-revealing, and a grouping conflicts with C3's one-operation rule.
- The only local `XUseCase` spellings are exemplars — a NestJS factory example and a test example — not normative rules. The Python exemplars are an unsuffixed operation class (`ApplyCoreRevision`) and module-level `execute()`.
- The recommended shapes are a recommendation, not current policy: TypeScript `<Verb><Object>UseCase` in `application/use-cases/<verb>-<object>.use-case.ts`; Python `<verb>_<object>.py` with `execute()` and an unsuffixed `<Verb><Object>` class only where a class is needed.
- At the research date there was no TypeScript application in this repository, so the NestJS convention is reference architecture, not evidence of local practice.

The governing feature `odd/tasks/domain-use-case-conventions.md` L2 (2026-10-29) records the concrete local findings from `implementation-review/task1/bastion1`: `query-verification/scripts/query_verification.py` holds two operations (`validate` and `evaluate`) in one module; `ticket-runbook/application/validate.py` and `verified-pr-cleanup/application/cleanup.py` carry naming defects (a generic module verb without its object, while the operation is `ValidateAnalysis`; and an operation module named for the activity rather than the outcome); and `ticket-runbook/entry.py` re-declares use-case classes under the same names as the application classes it delegates to. Unknown historical rationale for the existing exemplar spellings is unrecorded; no source is available showing why they were chosen.

## Decision

- **One use case per file/module; one public `execute()` per operation.** This restates the existing rule rather than creating it. Everything else in an operation module is a private helper (underscore-prefixed in Python). A module exposing two operations is nonconforming even when both are valid business operations.
- **Python.** The operation module is `application/<verb>_<object>.py` (`validate_analysis.py`, `preflight_branch_cleanup.py`), exposing `execute()`. The module path carries the operation, so a class is used only when state or injected collaborators justify one; that class is named `<Verb><Object>` with **no** `UseCase` suffix and exposes the single public `execute()`.
- **TypeScript.** The class is `<Verb><Object>UseCase` in `application/use-cases/<verb>-<object>.use-case.ts`, matching the existing `{entity}.entity.ts` / `{entity}.repository.ts` file style. It keeps the guide's existing constraints: one `execute()`, constructor-injected interfaces, no framework decorators, no thrown domain errors. The suffix is retained in TypeScript because the folder is not visible at controller, module, and test import sites.
- **The name states a business outcome.** Choose a verb-plus-object a domain expert would recognize (`ChangeShippingAddress`, `PlaceOrder`), not a table, endpoint, screen, or persistence verb. `Create`/`Update`/`Delete` are acceptable only in a genuinely CRUD-like domain; `ManageX` and `ProcessX` are not, because they name no outcome and hide whether a rule exists.
- **`Service`, `Manager`, `Helper`, `Processor`, and `Util` are not use-case names.** They name a layer, a grouping, or a mechanism rather than one operation. A `Service` grouping is structurally incompatible with the one-operation rule; `Helper`/`Util` usually signal a pure helper, which is not a use case at all — C7 exempts it, and a pure transformation keeps the exemption without an artificial `execute()` wrapper.
- **Composition roots and CLI routers may wire multiple operations.** An `entry.py`, `main.py`, composition module, NestJS module, or CLI router may construct adapters, select a mode, and call several operations. It must not re-declare a use-case class or a same-named wrapper over the application operation: that creates two types with one name, hides which one is authoritative, and reintroduces a second implementation surface. Wiring is not a second implementation.
- **Consistency.** Choose one shape per stack and apply it to every use case. A mixed vocabulary is itself a review finding; it usually indicates an unresolved decision about what the operations are.
- **Scope and ownership.** This ADR owns the rationale for use-case organization and naming. It does not change the layer contract, the one-file-per-use-case requirement, or the `execute()` requirement — those stay in `architecture/clean-architecture.md`, the backend shape, and the stack guides. This decision is realized in the architecture core (`C3` and the stack `Application operations` sections); this ADR is source-local rationale, not the definition owner.
- **Authorization boundary.** This is a documentation decision. It requires no rename, move, refactor, test edit, dependency change, permission change, or destination mutation. The evidenced defects are remediation items under `odd/tasks/domain-use-case-conventions.md` S5, to be handled only by a separate authorized feature with a current Bastion 🧱 (Backend & Scripts Architect) gate and applicable test evidence.

## Alternatives

- **Leave names unspecified and keep only "one named business operation".** Rejected: it constrains the unit but not the file or class name, and the evidenced drift (`validate.py`, `cleanup.py`, duplicate wrappers in `entry.py`) shows the gap is real. The rule would remain unenforceable at review time.
- **Use `<Verb><Object>` without a suffix in TypeScript as well.** Rejected for TypeScript: it is consistent with Python but inconsistent with the local exemplars and the test examples, and the folder is invisible at import sites. Python keeps the unsuffixed form because its module path already names the operation.
- **Add a `UseCase` suffix in Python too.** Rejected: redundant inside `application/`, and it diverges from the accepted unsuffixed exemplar `ApplyCoreRevision`.
- **`PlaceOrderHandler`, `PlaceOrderInteractor`, `OrderPlacer`.** Rejected: `Handler` imports MediatR/`handle()` semantics the local contract does not use; `Interactor` introduces a second vocabulary; `OrderPlacer` is an indirect agent noun.
- **`OrderService` as a grouping of related operations.** Rejected: it contradicts C3's one-operation rule and is exactly the shape the research record identifies as a layer name masquerading as an operation.
- **Name per endpoint, screen, or table.** Rejected: no source fixes that granularity, and the chosen unit is a business goal or transaction boundary.
- **Allow the composition root to keep same-named delegating wrappers for compatibility.** Rejected: it preserves two authoritative types under one name and can drift from the operation it wraps. No historical rationale for the wrappers is recorded, so none is asserted.

## Consequences

- Placement and discovery become predictable: a reader finds one operation per module and can infer its behavior from the name; review can flag a multi-operation module or a mechanism name mechanically instead of arguing style.
- Naming becomes a diagnostic, not proof. A well-named use case can still be anemic, and a CRUD name can be legitimate in a simple domain; this ADR does not convert a naming judgment into a behavior-placement judgment, which is [ADR 0004 — Domain behavior placement](0004-domain-behavior-placement.md)'s scope.
- Renames and splits carry a real cost — imports, tests, entry wiring, and any external invocation names — and are deliberately excluded here. Until that separate remediation lands, the evidenced defects remain known nonconformances to report, not exemptions to grandfather.
- The one-file/one-operation rule is unchanged and already published in the Python guide and the backend shape; the naming pattern, the wrapper prohibition, and the explicit composition-root allowance now live in the architecture core (`C3` and the stack `Application operations` sections). This ADR remains the rationale record.
- Unresolved and unrecorded: the appropriate granularity for simple single-entity reads (`Get<X>` is an acceptable read but weak business vocabulary), and any historical rationale for the existing exemplar spellings. No TypeScript application was found at the research date, so no TypeScript practice is verified. Status is `Proposed`: the user directed the operative definitions into the architecture core, so the core rule is in force; this ADR remains the rationale record pending explicit approval, and approval establishes a documentation contract, not code conformance. This source-local ADR is explanation, not an undistributed dependency of shared contracts.
