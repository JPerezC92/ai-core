## Context

Existing B1/B3 repository wording and F1's data-record terminology need reconciliation rather than competing definitions. The [research record](../../research/architecture/domain-model-repositories-and-naming/README.md) preserves prior source observations, source limits and accepted design resolutions; it is not a fresh source fetch or implementation audit.

The user authorized architecture definitions and related documentation only. Naming, immutable returns and folder growth are explicit design selections, not universal external mandates. No exhaustive local inventory or runtime conformance is established.

## Decision

Adopt the following shared rules in architecture owners, with language-specific mappings rather than duplicated normative text:

1. **Domain taxonomy and invariant ownership.** Define entity (stable identity and protected legal behavior), value object (identity-free value equality and immutable validity), aggregate (root-controlled consistency boundary), domain event (immutable fact already produced), domain service (domain behavior without a natural entity/value owner), pure rule module (cohesive IO-free functions), data-only record (data without a rule-bearing model claim), port (inward-owned external capability contract), and domain error (typed expected business failure). Classification asks what owns identity, invariants, transitions and effects, not merely whether a class exists. A root can protect child invariants; children need not duplicate root behavior. Publicly mutable domain-named bags whose rules live in callers are records or nonconforming models, not compliant entities.
2. **Immutable state changes.** Entity behavior validates a named transition and returns a new valid instance with the same identity or a typed domain error value. Protect nested collections/children and exposed aliases so mutation cannot bypass the root. Prohibit public setters and writable identity. Creation establishes new identity and creation rules; reconstruction restores identity and validates applicable state invariants without replaying creation effects. Functional rule modules remain valid; do not require artificial entity classes for records or calculations.
3. **Repositories and query ports.** Define a repository per aggregate-root type, not per object instance or child entity. Its domain port returns domain objects, an empty lookup for absence, and no raw rows; its infrastructure adapter maps persisted state explicitly. Repositories contain no business policy and commit nothing. Query ports may return domain-owned read projections rather than rehydrate aggregates; they do not expose storage records or transport payloads. A frontend service port is not automatically an aggregate repository, but frontend ports are not blanket N/A.
4. **Failures and transactions.** Preserve C5: expected business failures are typed values; arbitrary IO, parsing and programming exceptions remain exceptions. Only explicitly contracted persistence conflicts map to corresponding expected outcomes. The application coordinates transaction scope and commit/rollback across involved ports. A UoW abstraction is optional when needed; an existing session/transaction facility may suffice. No automatic handwritten-fake repository rule is introduced; the testing contract controls doubles.
5. **Events and delivery.** Domain events describe facts produced by successful domain behavior, not transport/integration messages. Integration mapping and delivery belong outside the domain. Coordinate persistence and publication so failed transactions do not publish successful facts. After-commit sequencing does not guarantee delivery: where reliable delivery is required, specify an appropriate persistence/publication strategy and its failure handling, without universally selecting a mechanism here. Aggregates and events bind where used; simple CRUD need not invent them.
6. **Business-owned layout and growth.** One rule-bearing type per module; no generic multi-concept `entities.py`, `models.py` or `value_objects.py` buckets. Keep an aggregate root, children, owned value objects, events and repository interface within its named business folder. At the second same-role module within that ownership boundary introduce its role subfolder there, never a global role folder that separates aggregate-owned parts. Pure function modules and intentional data records are not forced into entity roles or class quotas.
7. **Concept-role naming.** Use one shared vocabulary with Python `<concept>_<role>.py` and TS/JS `<concept>.<role>.ts` / `.js`, using native snake_case versus kebab-case concept spelling. Selected semantic roles are entity, value object, event, repository, port, domain service, policy, error, row, model, request, response, projection, record and query. The event filename is `order_placed_event.py` / `order-placed.event.ts` / `.js`, not a domain-event suffix. Classes retain business names such as `Order`; filenames disclose role. A pure function module names its predicate or calculation. An actual policy uses `pricing_policy.py` / `pricing.policy.ts`; an actual domain service instead uses `pricing_domain_service.py` / `pricing.domain-service.ts` (with corresponding `.js` spelling), not an ambiguous application service name. These roles are not interchangeable.
8. **Boundary vocabulary.** Name a raw database shape `OrderRow` (`order_row.py`, `order.row.ts/js`) and an ORM/persistence model `OrderModel` (`order_model.py`, `order.model.ts/js`), both in infrastructure. Name delivery shapes by action and direction, for example `CreateOrderRequest` (`create_order_request.py` / `create-order.request.ts/js`) and `OrderResponse` (`order_response.py` / `order.response.ts/js`). A domain-owned read projection uses `OrderSummary` (`order_summary_projection.py` / `order-summary.projection.ts/js`). Map each boundary shape through one explicit step to/from domain data; a domain `Order` is not a raw row or an API request. No unused wrapper is required merely to fill the vocabulary.

This source-local record explains the decision; it is not operative architecture authority. Explicit acceptance is recorded above; it authorizes no external publishing, implementation remediation, dependency changes or destination mutations.

## Alternatives

- Retain only immutable identity and factories: leaves legal state changes underspecified and does not prevent callers from owning domain rules.
- Use mutable entity setters: contradicts the selected immutable-transition model and permits bypass unless separately constrained.
- Require rich classes for all domain data: misclassifies projections, records and functional rules; the existing contract permits these representations.
- Repository per table/child or transaction-owning repository: breaks the selected aggregate boundary or distributes commit authority. Read projections remain a distinct capability, not a reason to impose aggregate loading on every query.
- Universal custom UoW, fake repository or delivery mechanism: adds mandates not established by the evidence or selected scope.
- Global role buckets or arbitrary size ceilings: obscure business ownership or fragment aggregates. Identical dotted Python/TS filenames: sacrifices native module conventions; the shared selection is semantic vocabulary, not identical punctuation.

## Consequences

The decision makes invariant ownership, persistence boundaries and role classification reviewable while preserving functional domains and conditional DDD applicability. Immutable nested-state protection and explicit reconstruction require concrete language mappings. Naming drift may require later migration, but this feature changes definitions only; separately verified drift may be recorded as debt without implementation remediation or implied on-touch authorization.
