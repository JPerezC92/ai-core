# ADR 0004 — Domain behavior placement

- **Status:** Proposed — pending review and explicit approval
- **Date:** 2026-10-29

## Context

The durable research record [`anemic-domain-model-and-use-case-naming`](../../research/architecture/anemic-domain-model-and-use-case-naming/README.md) (2026-10-28) is the evidence base for this decision. It establishes that an anemic domain model is **not** "a class with only fields": it is a domain-named model that claims to model the domain while its behavior lives elsewhere and the model still allows public mutation. DTOs, events, read models, and persistence records are data structures by design, and calling them anemic is a category error. The record also establishes that Clean Architecture constrains source dependency direction, not whether behavior is expressed as methods, functions, or a service; entities "can be an object with methods, or it can be a set of data structures and functions".

The local contract states the constraints this ADR works within:

- [`architecture/clean-architecture.md`](../../../architecture/clean-architecture.md) C2 keeps the domain framework- and infrastructure-free; C3 requires one named business operation with a single `execute()` and says "Policy belongs here or in domain, never in adapters or presentation"; C4 keeps business rules out of adapters and requires a single mapping/parsing step; C7 exempts a pure helper from any artificial use-case wrapper.
- The Python guide permits data-only constant modules and pure transformation functions in the domain, and backend entities as framework-free classes with underscore storage, per-field read-only properties, `@classmethod create(...)`, and immutable identity ([`architecture/stacks/python.md`](../../../architecture/stacks/python.md) → `Domain and ports`).
- The NestJS guide expects framework-free entity classes with `private readonly` fields, a getter per field, and a static `create()` factory ([`architecture/stacks/typescript/nestjs.md`](../../../architecture/stacks/typescript/nestjs.md) → `Domain and ports`).

The governing feature `odd/tasks/domain-use-case-conventions.md` L2 (2026-10-29) records the `implementation-review/task1/bastion1` review evidence. No repository-wide anemic OO model was evidenced. Within the paths reviewed in feature L2, the Python tooling used a functional-domain style — pure rules in `domain/` modules and orchestration in `execute()` operations — which C2 and C7 permit as a legitimate representation (b); that observation does not extend to unread paths, is not a repository-wide audit, and is not a claim that Python tooling is only functional modules. Later authorized work in [`odd/tasks/problem-register-entity.md`](../../../odd/tasks/problem-register-entity.md) (work-unit `5cda579`, closed 2026-10-29) added ticket-runbook `Problem`: a framework-free class with `create()`, named enums, and row-owned `is_incident` / `is_matchable` / `is_exact_match_eligible`. Invalid cells never become an entity. The prior mislabel — a TypedDict in `entities.py` with no behavior — is shape (c), not a legitimate record (a). Functional domain modules remain legitimate (b). Exactly one genuine policy misplacement was evidenced: `.opencode/skills/core-sync/scripts/core_sync_pkg/infrastructure/filesystem.py` → `preflight_write_targets(...)` decides write-target safety policy — it rejects symbolic links and non-regular files, aliased targets, root/destination escapes, and source-tree inode sharing — inside an infrastructure adapter. That finding is a separate remediation item; this ADR does not address it and no code is changed here.

Unknown historical rationale for individual placement choices is unrecorded; the research record is a documentary synthesis, not an independently reviewed study. No repository-wide audit was performed and no code conformance is claimed for any file, module, package, or destination; the repository evidence is bounded to the paths named in feature L2 and the later `Problem` entity work in `odd/tasks/problem-register-entity.md`.

## Decision

- **Classify before judging.** Separate three shapes that are routinely conflated: (a) data-only result, read, and boundary records — DTOs, read models, persistence records, events, configuration, typed intermediate data — which are data structures by design and not an anemic model; (b) functional domain modules — immutable typed data plus pure functions enforcing the rules — which are a legitimate domain representation under C2 and do not need classes; (c) a genuinely anemic domain model, where domain-named types withhold behavior while allowing mutation and the rules are enforced only by callers. Only (c) is a design finding. A TypedDict in `entities.py` with no behavior is shape (c), not a legitimate record (a). Do not report (a) or (b) as anemic, and do not convert them into classes or wrappers to satisfy a shape preference.
- **Enduring rules belong in the domain.** An invariant, validity rule, or legal state transition belongs in the domain — an entity/aggregate or a pure domain function — when it must hold regardless of entry point, when more than one use case must remember it, when it defines a legal transition, or when duplicating it would produce inconsistent behavior. Rules spanning several entities belong in a domain service or pure domain function, still framework-free.
- **Application-specific policy may stay in the use case.** Orchestration, transaction scope, authorization, idempotency, and a policy choice not intrinsic to the domain may live in the use case. C3 explicitly permits policy "here or in domain", and this ADR does not narrow that permission: single-caller policy that no other caller can bypass does not have to move inward preemptively. Move it when a second caller appears, when bypass becomes possible, or when the rule acquires an enduring domain meaning.
- **Adapters hold no business policy.** An adapter maps outside data to domain types through a single step and performs IO (C4). It must not decide validity, a legal transition, or an authorization outcome, and must not be the only place a rule is enforced. When such a decision is found in an adapter, the remedy is to move the decision to the application or domain and leave mapping/IO behind — not to document the adapter as an exception.
- **Preserve the entity contract.** Do not add public setters or writable identity to enable state change; the guides forbid them for backend entities. A state-transition convention (for example a domain method returning a new valid instance, or a pure domain function returning a typed result) is not selected by this ADR — the research record lists it as an open question. TODO: requires evidence and a separate design decision before any transition API is introduced.
- **Scope and ownership.** This ADR owns the rationale for domain behavior placement. `architecture/clean-architecture.md` remains the shared contract owner, and the stack guides remain the owners of concrete entity syntax. This decision is realized in the architecture core — `C3` plus the existing `Domain and ports` and `Adapters and delivery` text in the stack guides; the stack `Application operations` sections belong to ADR 0005. This ADR is source-local rationale, not the definition owner.
- **Authorization boundary.** The original decision authorized no code edit, refactor, test change, dependency change, permission change, or destination mutation. This update is documentation of later authorized code from `odd/tasks/problem-register-entity.md`, not a new code grant. The evidenced `core-sync` write-target policy remains unfixed and is remediated only under a separate authorized feature with a current Bastion 🧱 (Backend & Scripts Architect) gate and the applicable Crucible 🔥 (Test Architect) suite evidence.

## Alternatives

- **Require rich object-oriented entities with domain methods everywhere.** Rejected: C2 and both stack guides already accept framework-free classes *or* typed data plus pure functions, and the research record states Clean Architecture does not require rich OO entities. Mandating one representation would force a rewrite with no evidenced defect and would contradict the accepted Python functional-domain style.
- **Treat every data-only type as anemic and wrap it in an operation or class.** Rejected: a category error for boundary records, and it contradicts C7's prohibition on artificial wrappers for pure helpers. It adds indirection without adding an enforcement point.
- **Keep a thin domain and place all rules in use cases.** Rejected as a general rule. It is acceptable for genuinely simple, CRUD-like tooling with no invariants and one entry point, but it becomes the "clean but anemic" shape once invariants exist: every new caller must re-implement them.
- **Move all policy into the domain preemptively.** Rejected: it narrows C3's explicit dual permission, adds indirection for single-caller application policy, and confuses application concerns such as transaction scope and authorization with domain invariants.
- **Leave the write-target policy in the infrastructure adapter.** Rejected. The Bastion 🧱 (Backend & Scripts Architect) review cited in feature L2 classified it as policy rather than mapping/IO, and C3/C4 forbid policy in adapters. No historical rationale for its placement is recorded, so none is asserted.

## Consequences

- Reviewers gain a defensible distinction between a data structure by design and an anemic model, and a single placement question — where must every caller obey the rule? — instead of a style preference.
- No forced OO migration: the accepted functional-domain style stays valid, and existing data-only types are not reported as findings.
- An unresolved decision remains: no entity state-transition convention is selected. Until one is, teams must not add setters, and the "clean but anemic" risk stays a conscious choice rather than a resolved design.
- A known nonconformance is recorded but not fixed: `preflight_write_targets(...)` in `core-sync` infrastructure holds write-target policy. It is reported as a remediation item, not grandfathered as a legacy exemption; the fix requires a separate authorized feature and the usual gates.
- The evidence base is bounded: a documentary research synthesis plus the file-level review cited in feature L2, plus later authorized `Problem` entity evidence in `odd/tasks/problem-register-entity.md` (`5cda579`, closed 2026-10-29), with no repository-wide audit and no TypeScript application found at the research date. Placement judgment for unread paths remains unverified, and unknown historical rationale stays unrecorded.
- Status is `Proposed`: the user directed the operative definitions into the architecture core, so the core rule is in force; this ADR remains the rationale record pending explicit approval, and approval establishes a documentation contract, not code conformance. This source-local ADR is explanation, not an undistributed dependency of shared contracts.
